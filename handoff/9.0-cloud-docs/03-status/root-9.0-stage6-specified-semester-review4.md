## 决定

**有条件放行方案 A：指定学期从登录后教务首页的实际 `xnm`／`xqm` option 选择；选择的原始 value 原样用于请求。** 不允许把七个已观察的选项或 `1|秋` 等值硬编码为永久学期表。原有 `2026`、`3/12/16` 和「秋冬／春夏／短学期」三档退役；旧测试里确认这些硬编码值的断言要替换。无需保留未使用的 `ZjuTerm`／`ZjuManualSemester` 壳。现有自动读取路径仍从本次首页 option 提交请求。

### 实现时必须处理的流程边界

1. **先登录，后选择，再下载课表。** 旧 UI 在登录前选自由年份＋三档，但服务端 option 只能在认证后读取。指定学期的第一次操作完成认证和首页 option 读取，展示可选择的学年与学期；用户明确确认两项后，才用**同一个仅内存教务会话**请求课表。绝不能第一次操作完成后自动查询默认学期，也不能凭展示文字拼 value。界面应清楚区分“登录并读取选项”和“导入所选学期”。
2. 认证密码在登录请求结束后立即从 UI 和传入的 `CharArray` 清除；等待用户选学期时只能持有本次会话 Cookie 与 option 候选，不得持有密码。取消／离开／超时要废弃该会话；进程重建后不恢复会话或密码，须重新认证。一次会话只接受一次用户确认；异步回调需避免离开页面后发起课表请求。不要将账号、Cookie、原始 HTML、选项列表或响应写入日志、SharedPreferences、Room 或导航参数。
3. 两个下拉都要解析**全部非空且解码后仍非空**的 option，而非调用目前仅取 selected／第一项的 `parseSemesterOption`。界面用原始 value 作内部选中键；同显示文字的“短”用学期前缀或其它可读标记消歧（例如“短（1）／短（2）”），相同 value 重复或选择已失效都明确失败，不猜第一项。用户名、页面响应与会话仍走官方 HTTPS 域名校验及现有总超时。
4. 查询前校验用户选中的**两项 value 仍属于本次同一会话读到的 option 集**，缺失／重复／歧义则停在错误状态，不提交课表请求、不改查当前学期。服务端返回异常、登录失效或重新登录也不得拿上次 option 作请求；失败允许用户重新开始登录。
5. `xqmmc` 暂按现有 `value.substringAfter('|', text).ifBlank { text }` 规则派生；真实请求的 `xqmmc` 仍未取得，保留为待核对，不宣称已经验证。请求的学年／学期代码及显示值继续传给现有结果和候选元数据，不让响应回显替代请求值。

### 自动读取路径

**收紧一个已知误选边界**：若没有 selected 且存在多个不同非空候选，返回明确失败，不取第一个；只有唯一有效 option 时可直接采用。多个 selected 或重复 value 也失败。已有 selected 且唯一的正常路径保持原请求参数。这属于本次修正的回归测试范围；旧错误文案“可改用指定学期重试”在指定学期也依赖首页时应改为真实可行的重试建议。

### 证据问题

审计 §1.3 说学期文字共 **8 项**，列出“秋、冬、短、暑、寒、春、夏、短”，但其 §7 真正逐项记录的是 **7 项**，没有“寒”；README 仍写 8 项。此次只把 §7 的 7 项当作已观察选项，不能宣称“全部学期代码已取得”，需在用户电脑核对采样同一页面／同一时刻为何不一致，再更正文档。动态读取方案不依赖该缺项，但测试要允许未来新增选项而不改代码。重复“短”在 §7 是 `1|短` 与 `2|短`，不等于两者必定涵盖所有学校所称“短学期”。
