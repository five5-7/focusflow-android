## 一、诊断证据（dev-only 日志，release 不生效）

三次导入（含两次加装 gate-walker 后）稳定复现同一条记录：

```
stage=request  model=Qwen/Qwen3-VL-8B-Instruct at=00:43:58.719
stage=response model=Qwen/Qwen3-VL-8B-Instruct at=00:44:43.757 elapsedMs=45038
               outcome=text rawLength=5740
stage=parse    result=reject jsonKind=json-object
               jsonParseError=IllegalArgumentException:Failed requirement.
               schemaFailedField=geometry:keys=height,originalToWorking,periods,weekdays,width
               rawLength=5740
stage=shape    root={candidates,geometry}
               geometry={height,originalToWorking,periods,weekdays,width}
               candidateCount=12
               candidate[0]={box,day,endPeriod,evidence,geometryConfidence,id,note,
                             rawLocation,startPeriod,textConfidence,title,weeks}
               candidatesWithWrongKeys=0/12
```

### 任务要求的三项判定

| 判定项 | 结论 | 依据 |
| --- | --- | --- |
| 原始模型响应是否为空 | **不为空** | `rawLength=5740`（三次：5740 / 5812 / 5740） |
| 是否为 JSON | **是** | `jsonKind=json-object`，通过 `VisionJsonSyntax.valid` 严格语法校验，且 `JSONObject` 解析成功 |
| 哪个字段导致拒绝 | **`geometry.evidence` 缺失** | `geometry` 实际键为 5 个，schema 要求 6 个 |

### 关键补充事实

**`candidates` 完全合规**：`candidateCount=12`，`candidatesWithWrongKeys=0/12` ——
**12 条候选每一条的键集合都精确正确**（12/12 键齐全）。

也就是说，模型产出的响应**除 `geometry.evidence` 外整体结构完好**：
`width / height / originalToWorking / weekdays / periods` 全部给出，12 条候选字段齐全。
**唯一缺失的是 geometry 层的 `evidence` 数组**（而每条 candidate 内部**是带 `evidence` 的**）。

## 二、分类判定：B（主分类）

### 判定理由

`CourseVisionRecognizer.buildStructuredPrompt()` 中**明确列出**了该字段：

```
对象键必须是 geometry 和 candidates。geometry 键必须是 width,height,originalToWorking,weekdays,periods,evidence；
```

模型被明确要求输出 `geometry.evidence`，实际输出中没有。
**按定义这属于「模型输出不符合结构化要求」→ 主分类 B。**
即：**未满足当前结构化输出契约。**

### 同时记录的 schema 设计疑点（**本轮不改校验**）

`VisionResponseParser.parse()` 使用**精确键集合相等**作为门禁：

```kotlin
require(geometryObject.keys().asSequence().toSet() == geometryKeys)   // 多一个键、少一个键都直接失败
```

由此产生一个**设计疑点**（注意：**是疑点，不是已确认缺陷**）：

> 一个非数值型、非安全性的**说明性字段**（`geometry.evidence`）被设为**硬必需**，
> 导致一份 12 条候选全部键正确的响应被整体拒绝，
> 且用户只看到「模型没有返回严格的结构化视觉结果」，无法得知缺的是哪个字段。

**处置：本轮不改变校验。** 该项转入**独立的 schema 设计方案**另行评估（见第三节方案 2），
不与本轮 prompt 修订混在一起。

## 三、修复方案

> **硬约束（严格遵守）**：本轮**不修改业务逻辑**；不放宽任何安全校验、不自动写入课程、
> 不修改审核流程、不更换模型。
>
> **下一步只做两件事之一**：
> - **① 修订 prompt**（方案 1）—— 本轮之后可直接执行的唯一改动；
> - **② 提交独立 schema 设计方案**（方案 2）—— 作为**独立交付物**另行评估，
>   **本轮不改变校验**，不与 prompt 修订捆绑。

### 方案 1（下一步唯一可执行项）：把 prompt 的「散文键列表」改为「显式 JSON 模板」

**问题**：当前 prompt 用一段密集散文列举 6 + 4 + 12 个键名，小参数模型（8B）在长键列表中漏项是已知倾向。
证据支持这一点：模型**记住了 candidate 内的 `evidence`，却漏了 geometry 层的 `evidence`** —— 典型的长列表漏项，而非能力不足。

**改法**：在 prompt 中直接给出**最小合法骨架**（键齐全、值用占位），并保留原有语义约束：

```
只返回如下形状的 JSON（键名与层级必须完全一致，值替换为识别结果）：
{"geometry":{"width":<int>,"height":<int>,
  "originalToWorking":[9 个 0..1 数字],
  "weekdays":[{"index":<1-7>,"start":<0..1>,"end":<0..1>,"source":"detected"}],
  "periods":[{"index":<1-20>,"start":<0..1>,"end":<0..1>,"source":"detected"}],
  "evidence":["<判定依据文本>"]},
 "candidates":[{"id":"...","title":"...","day":<1-7|null>,"startPeriod":<int|null>,
  "endPeriod":<int|null>,"box":{"left":0,"top":0,"right":0,"bottom":0}|null,
  "evidence":["..."],"rawLocation":<string|null>,"weeks":[<int>]|null,
  "note":<string|null>,"textConfidence":<0..1|null>,"geometryConfidence":<0..1|null>}]}
```

要点：
- 模板里 `geometry.evidence` 与 `candidates[].evidence` **同时出现**，消除「只在候选层给 evidence」的歧义；
- 保留「看不清用 null、box 不给猜测坐标」等原有硬约束文字；
- 模板**不是**放宽校验，它只是把已有要求表达得更可执行。

### 方案 2（**独立交付物，本轮不改校验**）：schema 设计 —— 区分「安全必需」与「说明性元数据」

> 性质说明：本节回应第二节记录的**设计疑点**。
> **它是独立的设计提案，不在本轮实施，也不作为 prompt 修订的前置。**
> 是否采纳、何时采纳，需单独决定。

在 `VisionResponseParser` 中把键集合检查拆为两层，**安全相关的检查一律不放宽**：

| 层级 | 字段 | 建议 |
| --- | --- | --- |
| **安全必需**（缺一即拒） | `geometry.width/height/originalToWorking/weekdays/periods`、`candidates[].id/title/day/startPeriod/endPeriod/box` | **保持严格**，缺失仍旧拒绝 |
| **说明性元数据** | `geometry.evidence`、`candidates[].evidence/note/rawLocation` | 缺失时按空值处理，**不影响几何与坐标校验** |

**明确不放宽的部分**（本方案不动）：
- `geometry.valid()`：宽高范围、`originalToWorking` 必须 9 个有限数、weekdays/periods 的 index 范围与唯一性
- `VisionBox.valid()`：坐标必须有限且落在 0..1、`left<right`、`top<bottom`
- `VisionCandidate.valid()`：day 1..7、节次 1..20、`end>=start`、置信度 0..1、weeks 1..60 且不重复
- 候选 id 唯一、候选数 ≤ `MAX_CANDIDATES`
- 坐标可信度清单与「不做默认星期/节次补齐」的既有口径

### 方案 3（配套）：把失败原因变成可执行信息

现状：任何门禁失败都折叠成同一句「模型没有返回严格的结构化视觉结果」。
本轮诊断已证明**失败字段是可确定的**（`geometry:keys=…`）。

建议把 `explainSchema()` 这类**结构性**原因接进用户可见文案，例如：
> 识别结果缺少 `geometry.evidence` 字段，未导入。可换更清晰的课表截图，或在设置中更换视觉模型。

该改动**不是**放宽门禁，只是把已经拒绝的事实说清楚；诊断本身仍只在 debug 构建输出（用户可见文案只带字段名，不带响应内容）。

## 四、验证该方案是否奏效的判据（下一轮用）

修复后重跑同一张照片，满足以下任一即视为通过：

1. `stage=parse result=ok`，且进入「检查课表识别」对话框；或
2. 仍失败，但 `schemaFailedField` 变为**安全必需字段**（说明说明性字段问题已解决，剩的是实质问题）

若 `geometry:keys` 仍稳定失败，则方案 1 未奏效，应回到 prompt 侧继续收敛（例如把模板再简化、或分两步请求）。
