## 二、根因（代码级确证）

`app/src/main/java/com/sakata/focusflow/VisionServiceModels.kt`：

```kotlin
object VisionLimits {
    const val SESSION_MS = 120_000L      // ← 整场识别的硬预算
    const val MAX_REQUESTS = 8
    ...
}
```

`VisionServiceClient.kt`：

```kotlin
fun cancelled() = stopped.get() || clock() - started >= VisionLimits.SESSION_MS
```

**关键结论**：

1. **per-request 超时可配（5–120 秒），但整场会话预算是固定的 120 秒**；
2. 维护者把 per-request 超时设为 120 秒后，**两个上限相等** —— 会话预算先到期，
   于是失败模式从「请求超时」变成「会话失效」，**配置旋钮实际上被会话上限封顶**；
3. 现象完全吻合：真实照片跑到 **~98 秒**后失败（请求 + 开销已贴近 120 秒会话上限）；
4. 这解释了第6轮合成图的失败为何与第7轮不同（56s/84s 撞结构化门禁，98s 撞会话预算）——
   **不是产品随机行为，是两道不同门禁在不同耗时下先后生效**。
