## 二、为什么跳过「删除服务」（重要，与授权时的理解不同）

维护者授权执行 A10，但我读代码后确认**删除内置服务不可经 UI 恢复**，故未执行该子项：

`VisionServiceStore.read()`：

```kotlin
val raw = prefs.all["configuration"]
if (raw == null) {          // ← 仅当 configuration 键「不存在」时才重建内置档案
    return Ready(VisionServiceConfiguration(listOf(VisionServiceProfile(
        "siliconflow", "硅基流动", "https://api.siliconflow.cn/v1", migrated,
        VisionCredentialStore.SHARED_REF, "legacy-1"))))
}
```

`VisionServiceStore.delete()` 写出的是 `profiles = []`（**键仍存在，只是数组为空**），
因此 `raw != null`，**内置档案不会被重建**。

后果链：

1. 「删除服务」后应用**零服务**，且不会自愈；
2. 用户只能通过「新增服务（下方填写）」手工重建，但新档案的 `credentialRef` 是
   `vision-<新UUID>`，**不再是 `SHARED_REF`**；
3. 于是「共享 key」与视觉服务脱钩，「学习路径建议」与课表识别**不再共用同一把 key**，
   与文档承诺的「共享 key 同时用于两者」不一致；
4. 除清除应用数据外，**没有 UI 路径把它恢复成出厂的内置档案形态**。

**结论**：该子项风险与收益不成比例（只为一个文案，换来不可逆的配置形态改变），
已跳过并在验收记录中注明原因。若确需覆盖，建议在**可抛弃的测试机**或清数据后的环境执行。
