### 【P2-1】独立提醒使用非精确闹钟，允许最长约 3.3 分钟延迟

- **现象**：`dumpsys alarm` 显示 `STANDALONE_DUE` 为 `RTC_WAKEUP`，但带投递窗口。
- **复现步骤**：新建独立提醒后执行 `adb shell dumpsys alarm | grep -A6 STANDALONE_DUE`。
- **实际结果**：
  ```
  type=RTC_WAKEUP origWhen=2026-10-01 22:55:00.000
  window=+3m19s192ms
  maxWhenElapsed=+6m40s429ms
  exactAllowReason=policy_permission
  ```
  即系统被允许把 22:55:00 的提醒推迟到 22:58:19（最坏 23:01:40）才投递。
- **预期结果**：提醒类闹钟应使用精确闹钟（应用已声明并获批 `USE_EXACT_ALARM`），窗口应为 0。
- **实际本次观察**：延迟仅 ≤8 秒（远好于窗口上限），但**窗口本身仍存在**，在 Doze/省电策略更激进时会兑现为分钟级延迟。
- **等级**：P2
- **建议**：核对调度代码是否走了 `setWindow(...)` 或非精确 `set(...)` 路径；既然已持有 `USE_EXACT_ALARM`
  且已加入电池白名单，用户可见提醒宜使用 `setExactAndAllowWhileIdle`。需要更多样本（Doze 状态下）才能定性延迟上限。

### 视觉导入链路的实测汇总（阶段8 批次B/C 的阻塞证据）

| 输入 | 超时 | 结果 | 耗时 |

| 合成图 ×2 | 120s | `模型没有返回严格的结构化视觉结果` | ~56s / ~84s |
| **真实照片 ×2** | **120s** | `已取消、超时或服务配置发生变化，本次未导入` | **~98s** |

**7 次导入，0 次进入「检查课表识别」对话框。**
期间**未写入任何课程**、既有课程未污染、失败均有明确文案（fail-closed 行为正确）。

**代码级根因**：`VisionLimits.SESSION_MS = 120_000L` 是整场识别的硬预算，
`VisionServiceClient.cancelled()` 在其到期后拒绝继续；
把 per-request 超时设为 120s 后两个上限相等，**会话预算先到期**，
因此再调大 per-request 超时不会改善结果。
