## 3. 缺的两个动作，以及各自真正难在哪

### 3.1 移入收集箱（`移入收集箱`）
把提醒变成一个收集箱条目（`Item` + `CaptureRoute.INBOX`，见 `CoreModels.kt:69`）。

难点**不在按钮**，在写入：
- 动作由 `BroadcastReceiver` 在后台触发，要写**用户数据**（新增一个条目）；
- 必须走与前台同一条写入路径（`CoreDataRepositoryOperations` 系列），并遵守既有失败契约：
  **失败就什么都不做、不清空、不重建**；
- **幂等**：同一动作被点两次（或通知重建后又被点）只能产生**一个**条目；
- **陈旧拒绝**：提醒已完成/已稍后/已过期时，动作必须被拒（沿用 `expectedAt` 口径）；
- **动作后提醒的去向要定**：变成条目后，这条提醒是"完成"（推荐，语义清楚）还是保留？

### 3.2 开始（`开始`）
语义**未定**，这是本组最大的待定项：是"开始一次活动会话"（`ActivitySession`）、还是"开始推进某个计划/任务"？
两者写入路径与撤销语义完全不同。**在定稿之前不实现**——按 AGENTS.md，通知行为必须保守，猜错会让用户在通知栏里误触发后台写入。

## 4. 必须先定稿的四个问题（交回用户）

1. **动作集合**：只要"移入收集箱"，还是同时要"开始"？（Android 折叠视图最多 3 个动作，当前已有 2 个 ⇒ 最多再加 1 个）；
2. **"开始"的含义**：活动会话 / 计划推进 / 其它？（若选不出，建议**本组只做"移入收集箱"**，"开始"另开检查点）；
3. **动作后提醒的去向**：移入收集箱后是否同时把提醒标记完成？（推荐：是——否则用户会收到"已完成的事"的二次提醒）；
4. **撤销**：移入收集箱要不要"撤销"？（推荐：不做，但条目本身可以在收集箱里删除——这本就是既有能力）。

## 5. 绝不能动的东西（授权边界）

- 通知渠道 ID 与通知标签（`CHANNEL_STANDALONE`、`standalone:$id`）：用户可见契约，**不得新增渠道**。
- **稍后语义**（不改原设定时间）、**一次性临时静音**、**陈旧动作拒绝**（`expectedAt` 比对）：三条都不得弱化。
- 通知保守性：被忽略或过期的提示不得反复回来（AGENTS.md 明文）。
- `standalone_reminders`/`entries` 的 JSON 字段：只能加、不能改；新增字段必须有默认值。
- Room 保持不激活；不改 `Item` 的既有字段语义。

## 6. 第一件可独立交付的东西（**已实现，2026-09-29**）

**纯函数 + 单测**（与组②/③同构，不接线、不写存储）。**已实现，2026-09-29**：
`app/src/main/java/com/sakata/focusflow/StandaloneActionPlans.kt`（`internal object StandaloneActionPlans`）+
`app/src/test/java/com/sakata/focusflow/StandaloneActionPlansTest.kt`（**21 项**）。

API（比草案多给了一个纯应用函数，便于把"状态会变成什么样"也测出来）：

- `plan(reminder, action, now, expectedAt, deliveredAt, snoozeMinutes, completeAfterMove) -> StandaloneActionPlan`
- `applyTo(reminder, plan) -> StandaloneReminder`：**纯数据**变换，不写存储；
  对 `Rejected` 抛 `IllegalStateException`（拒绝的计划不该被施加，别静默）；"移入即完成"却没给完成时间则抛错。

**参数默认值（文档此前漏写，补上）**：`deliveredAt = reminder.deliveredAt`、`snoozeMinutes = 10`（与既有实现一致）、
`completeAfterMove = true`。其中 **`completeAfterMove = true` 等于把本件 §4 问题 3 的"推荐"当成了默认值**，
而 §4 那四个问题**仍未定稿** ⇒ 接线前必须确认；要改成默认不完成，只需把默认值改为 `false`（一处改动 + 用例已覆盖两种取值）。

**允许范围**：`snoozeMinutes in 5..180`（与既有 `snooze()` 逐字一致），越界即拒绝。

**四类输出都带 `reason`**（`Completed`/`Snoozed`/`MovedToInbox` 也有）：供确认界面直接展示人话理由（与组②同口径）。

输出四类之一：
- `Rejected(rejectReason, reason)`：陈旧动作（`expectedAt != scheduledAt`）、已完成、稍后要求"已投递"却未投递或投递时刻不符、稍后分钟数越界、**"开始"语义未定稿**；
- `Completed(completedAt)`；
- `Snoozed(snoozedUntil)`：**只改下一次通知时间，`triggerAt` 不变**（由 `applyTo` + 测试钉住）；
- `MovedToInbox(draft, completesReminder, completedAt)`：收集箱**草案**（标题 + "来自提醒"来源标记），写入留给下一个检查点。

守卫逐条**镜像现有写入函数**（`StandaloneReminders.complete/snooze` 的前置条件），故纯函数与真实路径同口径。

**测试与变异**（`app/src/test/java/com/sakata/focusflow/StandaloneActionPlansTest.kt`，**21 项**；四点变异已全部按预期变红）：
| 破坏性编辑 | 红了几项 |
|---|---|
| 去掉陈旧动作守卫 | 2（"旧通知动作一律拒绝"、"稍后提醒以 snoozedUntil 为当前时间"） |
| 去掉"已完成"守卫 | 3（重复完成、已完成仍移入、拒绝计划不被施加） |
| 让稍后**顺手改 `triggerAt`** | 1（"不得改原设定时间"） |
| 把"开始"改成**允许并给出非空 reason** | 2（两条 START 用例，输入**不同**：已投递 / 从未投递） |

> 第 4 行的措辞很重要：如果"改成允许"时**连 reason 也留空**，`every action has a non-empty explanation`
> 会额外变红（3 项）。本表记的是实测形态（允许 + 非空 reason）⇒ 2 项。

**21 项覆盖内容**：完成（记账、未投递也允许、已完成拒绝）、陈旧动作（对每种动作都测）、稍后
（只改下一次时间且不动 `triggerAt`、分钟数上下界与越界、未投递、投递时刻为 0/负、投递时刻不符）、
移入收集箱（草案标题与来源标记、默认同时完成、可改为不完成、已完成仍移入被拒、同输入两次结果一致）、
"开始"（已投递与未投递两种状态都拒绝）、施加计划的契约（拒绝的计划抛 `IllegalStateException`、
不一致的移入计划抛 `IllegalArgumentException`）、以及**源文本守卫**（实现文件不得出现
`import android`/`SharedPreferences`/`AlarmManager`/`PendingIntent`/`notify(`）。

**未实现的（如实登记，不冒充已覆盖）**：设计草案里曾提"过期很久的提醒不允许再产生条目"，
本件**没有**实现任何时间窗规则——只按 `expectedAt` 判断动作新旧。若将来要有时间窗，属新增规则，
需先定"多久算过期"，并同时改守卫与测试。
