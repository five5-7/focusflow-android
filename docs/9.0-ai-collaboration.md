## 3. 协作规则（长期有效）

1. 计划 → 实现 → 审查依次进行；同一时间只有一个写代码者。
2. 审查者只读且独立（不同模型族）；审查模型不兼实现者。
3. 一次只给一个外部 AI 一个任务边界；并行必须使用独立 worktree、互不重叠文件。
4. 密钥只放环境变量或 OpenCode 凭据库；仓库文件只引用 `{env:...}`，不写明文。
5. 测试、CI、真机是唯一验收证据；未执行必须写“未执行”。
6. 高风险（课程身份、Room 迁移、通知调度、恢复性删除）先由主模型审定设计与失败回滚，再实现。
7. 提交、推送、发布仍需用户确认；每批提交后导出时间戳 bundle 并登记 `D:\focusflow\backups\backup-log.md`。
8. 本文件与《AI 使用手册》《实施计划》《AI 交接单》同步维护；配置变更必须同步到本文件，保证可复现。

## 4. 自动化分级与路线

- **L1（已落地）**：角色分工 + 模型路由 + 只读审查权限 + 内置搜索；提交/推送/发布人工确认。
- **L2（2026-09-27 本地实现；`review-gate`／`review_stage` 已实景烟测通过，整体分项结果见第 5 节）**：
   1. 提交前自动审查：`review-gate.js` 拦截 `git commit`，对暂存差异调用配置的审查子代理（`review-gate.json` 的 `agent`，当前 `review-kimi`）；同一 diff 哈希只审一次；判定为缺陷时阻止提交并把缺陷回传；审查模型/网络不可用时放行并提示（fail-open），不静默缓存为通过。`git add && git commit` 组合命令会被要求拆分执行。另提供 `review_stage` 预审工具：提交前对暂存差异后台审查（大 diff 按文件分片并行，每片附完整改动文件清单；分片失败按 fail-open 聚合，整体记 error——放行该次提交但不写通过缓存，同一 diff 再次提交会重新审查；有 unparsed 片则阻断），完成后写入同一 diff 哈希缓存；提交命中 clean 缓存瞬时放行、命中 defects 缓存阻止；预审与提交均按当前暂存差异的哈希匹配，暂存改变后哈希不同会重新审查、不套用旧结果；提交时若同一哈希已有预审在跑则等待其结果而不重复开审查会话。
  2. 后台任务工具：`bg-tasks.js` 提供 `bg_start`（命令先经 bash 权限规则校验）、`bg_status`（状态、耗时、日志尾部）、`bg_stop`（Windows `taskkill /T /F`）；完成/失败弹 TUI 通知；上限 4 个并发、保留 30 条记录。
  3. 模型发现：`siliconflow-discovery.js` 启动时用缓存（6 小时）同步 `/v1/models?sub_type=chat`；把已下线模型从本次运行白名单移除并警告，全不可用时保持原配置；默认不自动新增模型，配置 `siliconflow-discovery.json` 的 `include` 通配符后才按模式扩展（替代逐条手写）。
  4. 通知强化：`opencode-notify` 已覆盖需确认（权限/提问）、失败（`session.error`）与完成（`notifyOnIdle`）；本轮仅核对配置，无新插件。
  以上均**不自动 commit/push/发布**；审查者只读且独立。
- **L3（不允许）**：自动循环修复、自动提交或发布；与“未经确认不合并/发布、高风险先审定”的仓库规则冲突。
