# FocusFlow 6.5.0：历史事件与统计准确性

版本：6.5.0 / versionCode 467（版本号唯一来源 `app/build.gradle.kts`；CI 以 versionName 命名 APK）
分支：`agent/focusflow-6.5-history-events`（基于 `35c8b7d FocusFlow 6.4`；6.4.0 未单独发布，功能随 6.5.0 交付）
配套文档：数据结构约束见 [6.1-data-contract.md](6.1-data-contract.md)；版本路线图见 RoadmapData.kt / CHANGELOG.md。

---

## 1. 为什么做（背景问题）

6.5 之前的所有统计都从**当前任务状态倒推**，导致四个失真点：

| 问题 | 现象 |
|---|---|
| 删除任务 | 任务被硬删除后，它当天/本周的完成记录、改期记录一并消失，完成率反而被动升高 |
| 放回收集箱 | “未完成任务放回”与“完成”在统计上无法区分 |
| 改期 | 无历史可查；无法知道到底改了几次、改到哪一天 |
| 已完成任务再移动 | 移动会重置一部分状态，完成记录可能丢失或重复计数 |

用户开发计划文档《FocusFlow_未来开发计划.md》对 6.5.0 的定义是：**统计基于发生过的事件而不是当前任务状态倒推**，并建立统一历史记录。

## 2. 更新内容（对用户可见）

1. **统计口径变更**：今日计划完成率、今日完成数、今日改期数不再随删除/放回/移动倒改；已发生的事实保留在数字里。
2. **计划 → 历史记录**（新子页）：
   - 近 7 天逐日卡：每天显示「周几 / 完成率 / 完成 × 计划」；
   - 最近事件列表（最多 50 条）：创建、安排、改期、完成、放回收集箱、删除、恢复，按时间倒序。
3. **计划主页入口**：显示「近 7 天完成 N 项 · 改期 N 次」。
4. **本周回顾联动**：执行概览（计划完成率/改期/待恢复）同样改为事件驱动。
5. **存量迁移**：首次启动自动把旧存档中可可靠推断的事件补齐，行为对老用户无感。
6. **通知动作补记**：通知栏完成/最低版本/延后一小时/跳过 现在都与页内操作一样留痕。

## 3. 实现过程与逻辑

### 3.1 事件模型（TaskHistory.kt，纯 Kotlin，可单测）

```
TaskEvent(id, itemId, type, recordedAt, title, scheduledAt, extra)
```

8 种类型（`TaskEventType`，storageKey）：

| 类型 | 触发入口 |
|---|---|
| `task_created` 任务创建 | 快速记录（今天/明天/收集箱）|
| `task_scheduled` 任务安排 | 排入日程（目标排入、弹性安排、收集箱安排、收集箱保窗口、弹性计划初步安排）；目标自动排 |
| `task_rescheduled` 任务改期 | 页内改期；通知“延后一小时” |
| `task_completed` 任务完成 | 完成弹窗、今日/日程完成按钮、通知完成/最低版本 |
| `task_uncompleted` 取消完成 | 预留类型：当前无触发 UI，为语义完整而定义 |
| `task_to_inbox` 放回收集箱 | 恢复入口“放回”、跳过、错过的目标任务自动放回 |
| `task_deleted` 删除任务 | 放弃任务、日程页删除 |
| `task_restored` 恢复任务 | 暂停项目 → 恢复 |

设计选择：
- `itemId` 用于按任务**去重**；删除任务后事件仍保留（事件本就是历史）。
- `scheduledAt` 是安排/改期的目标时刻，是整个完成率分母的归日依据。
- `title/extra` 只为展示（`M月d日 HH:mm · 任务安排 · 标题 · 说明`），不参与统计。

### 3.2 存储与编码

- 新 SharedPreferences key：`task_events`（未复用 `baseline_events`）。
  - `baseline_events` 语义是“用户确认的原始习惯事件”，且 `resetBaseline()` 会整表清空；任务历史混入会被习惯基线重置连带抹掉，而且旧表只有 3 种任务事件、500 条上限、无 itemId/目标时刻，无法支撑归日去重。
- 上限 **1000 条**，追加保存（`appendTaskEvent`，取 `loadTaskEvents(1000) + 新事件` 的后 1000 条）。
- `TaskEventCodec`：写入完整字段；读取全部 `opt*` 且**未知 type / recordedAt≤0 的条目直接丢弃、不回写**——符合 [6.1 数据契约]的损坏降级策略。

### 3.3 一次性迁移（幂等）

`PrototypeStore.migrateTaskHistory()` 在 `FocusFlowApplication.onCreate()` 中执行（早于任何 UI 读 items），标记 key `task_history_migrated_v65_0`，内存/磁盘双保险幂等。

只补**可可靠推断**的事件（`TaskHistoryMigration.buildEvents`）：

| 旧字段 | 推断事件 |
|---|---|
| `completedAt` | 任务完成（extra = completionLevel，空则"完成"）|
| `lastRescheduledAt` | 任务改期（scheduledAt = 当前安排时刻）|
| `recoverySourceScheduledAt` | 任务安排（scheduledAt = 该时刻；**不**再补一条"放回收集箱"配对事件——放回时刻不可推断）|
| `scheduledAt` | 任务安排 |

**不制造假统计**：已删除的任务（硬删除无痕迹）、多年前的多次改期、放回的时刻——都不可能从现有字段恢复，一律不补。迁移只增不改，不影响 6.4 已锁定的 items 字段语义（恢复建议、日程显示、任务字段仍全部保留并正常读写）。

### 3.4 各统计的新定义

| 指标 | 定义 |
|---|---|
| 计划数（某天）| type ∈ {创建, 安排, 改期} 且 scheduledAt>0，按 **scheduledAt 归日**、itemId 去重 |
| 完成数 | 完成事件按 **recordedAt 归日**、itemId 去重（含已删除任务的完成时刻）|
| 完成率 | 完成数 ∩ 日计划数 / 计划数；无计划 → null（沿用"无计划不显示 0%"）|
| 改期数 | 当天改期事件条数（不去重，含"延后一小时"）——"发生了多少次改期" |
| 日程变化 | 当天 {安排,改期,放回,删除,恢复} 事件条数 |
| 周计划/周一完成 | 与上同，但窗口改为 `WeekReview.weekStartOf(now) + 7 天`，按 itemId 去重跨天移动 |

关键推论（都对应单元测试锁定的行为）：
- 同日多次移动（安排→改期→再改）只计 **1** 个当天计划；
- 改期到别日：**原日保留、别日 +1**（两个"发生过"的事实）；
- 放回收集箱 / 删除：**不撤当日分母**，且放回≠完成，完成率只受真实完成影响；
- 删除已完成任务：它的完成记录仍计入当日/当周；
- 恢复任务：不重复计已删任务（删除→恢复只算一条历史链，不再凭空 +1 计划）。

### 3.5 与旧逻辑的关系（零破坏）

新重载 `DailyLoopStats.summarize(items, now, taskEvents)` 与 `RecoveryInsights.weeklySummary(items, now, taskEvents)`：
- **task_events 为空 → 直接回退旧的 items 推导**（`summarize(items, now)` 等），新安装/迁移前行为与 6.4 完全相同；
- 非空 → 按上面的定义统计；
- Kotlin 侧同名多态选择，JVM 侧用 `@JvmName("…WithTaskEvents")` 分离方法签名（`List<TaskEvent>` 与 `List<BaselineEvent>` 擦除后同为 `List`，否则编译期平台声明冲突）；
- 原有的 2 参 `summarize`、3 参 `weeklySummary(items, now, events: List<BaselineEvent>)` 签名与全部现有调用零改动，6.4 的 30+ 测试原样通过。

### 3.6 接线清单（页内 15 处 + 通知 4 处）

- 快速记录 → 创建（今天只记类型，明天写入 scheduledAt）；
- 目标排入/弹性安排/收集箱安排/保窗口/弹性计划初步安排/目标自动排 → 安排；
- 完成弹窗（全完成/最低版本）、今日与日程完成按钮 → 完成（extra = 等级或"完成"）；
- 页内改期、通知"延后一小时" → 改期（延后**故意不动** `item.rescheduleCount`：它是"反复改期恢复建议"的阈值字段，保持 6.4 语义；事件只服务于统计）；
- 恢复入口"放回"（含缩为 15 分钟前身动作）、跳过、"错过的目标任务自动放回"（recoverMissedGoalTasks）→ 放回收集箱；
- 放弃、日程页删除 → 删除；
- 暂停 → 恢复。

### 3.7 历史 UI

- `PlanPage.HISTORY("历史记录")` 加入计划主页；hub 概要行 = 近 7 天完成/改期合计；
- `PlanHistorySection`：7 天逐日卡（今天高亮）+ 最近 50 条事件；
- 数据一致：MainActivity 的 `taskEvents` 状态通过 `recordTaskEvent()` 追加事件并即时重读（不少操作是 `saveItems()` 之后再记事件，若只靠 `saveItems` 刷新会**漏掉最后一条**，表现为"完成了但今日记录不显示，重启后才出现"）；`saveItems` 作为统一写入口同样顺带重读；App 从后台回到前台（ON_START）时再重读一次，覆盖通知栏后台动作（完成/最低版本/延后/跳过）在无活动持有期间的写入。

## 4. 范围边界（本版不做）

- `task_uncompleted`（取消完成）只预留类型，无 UI；
- 不把任务事件并入"习惯事件浏览"；不做导出；
- `task_events` 上限 1000 条、追加式、无索引（与 `baseline_events` 同量级策略）；
- 不做周统计扩展（跨日完成率等），留待后续版本；
- 统计数据不上传，仍只存本机（数据契约第 13 行：key 与凭据不入日志/夹具/版本库——事件含任务标题，同样遵守）。

### 5.1 真机验收记录与验收期修复

验收用一次干净链路（`快速记录 → 安排 19:00 → 完成`）在设备上逐步核对 SharedPreferences 中的 `task_events` 落盘与今日卡片：

| 检查点 | 结果 |
|---|---|
| 快速记录后 `task_created` 落盘 | ✅（事件 14→15，进程存活，logcat 无 FATAL）|
| 安排后 `task_scheduled` 落盘（extra=日期标签）| ✅（15→16）|
| 点「完成」后 `task_completed` 落盘，**同屏记录卡即时出现** | ✅ 记录卡显示 `15:02 · test-67 · 完成`，今日完成 5→6 |
| 计划主页 hub 行 | ✅ 近 7 天完成 6 项 · 改期 2 次 |
| 历史记录子页 7 天卡 | ✅ 周日（今）100% 5/5、周六 0% 0/1（昨晚安排的"测试"按安排日归周六，符合文档定义）|

验收期发现并修复的两个问题（均**未被**单元测试覆盖——纯 Kotlin 统计层测试触不到 Compose UI 与真机布局，说明 UI 路径必须靠真机验收兜底）：

1. **`recordTaskEvent` 自递归（致命）**：批量把 16 处 `store.appendTaskEvent(` 改写为 `recordTaskEvent(` 时，替换吃掉了函数体自身的第一行，变成 `recordTaskEvent(event)` 调用自己 → 任何事件写入都 StackOverflowError → 应用瞬间退出（表现为"点完成回桌面、无 FATAL、事件全没落盘、items 却更新了"）。修复为函数体内调用 `store.appendTaskEvent`；样式：新函数引入时不能通过全文替换旧调用改签名。
2. **历史页 7 天卡 `100%` 换行串行（布局）**：一行 7 卡在 4x 密度（1440px/360dp 宽）屏幕上每卡内容宽仅约 40dp，周日 `100%`（labelLarge Bold）恰好超宽被拆成两行，挤得 `5/5` 下沉 80px、与周一~六不对齐。修复：百分比改用 `labelMedium` Bold + `maxLines=1`，单元格间距 4dp→2dp；已验证与其它卡三行完全对齐。后续若要支持系统字体放大（font_scale>1），建议改为两行卡布局（4+3）。
