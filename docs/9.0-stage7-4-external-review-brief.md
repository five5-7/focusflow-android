## 2. 与本决策相关的代码事实（全部实测）

### 2.1 「受影响实例」集合在删除时没有被记录

**【实测】** 删除重复规则的真实链路：

| 跳 | 位置 | 行为 |
| --- | --- | --- |
| UI | `app/src/main/java/com/sakata/focusflow/TodoUi.kt:208-235` | 「重复规则」列表；`"stop"` 字面量 `:221`，`"delete"` 字面量 `:233`（确认框 `:230-235`）；行内按钮只在 `template.kind == "重复模板"` 时渲染（`:217`） |
| 分发 | `app/src/main/java/com/sakata/focusflow/MainActivity.kt:1664-1671` | `"delete" -> RepeatActions.deleteRule(items, template)`（`:1667`），随后 `if (result.events.isNotEmpty()) saveItemsWithEvents(...)`（`:1670`） |
| 删除规则 | `app/src/main/java/com/sakata/focusflow/RepeatActions.kt:149-158` | 先调 `stop`（`:150`）；若 `stop.events` 为空则原样返回（`:151`）；否则模板改为 `kind="回收站"`、`detail="重复规则已删除"`、`trashedAt=at`、`trashSnapshot=ItemsCodec.encode(listOf(template))`、`repeatFrequency=""`（`:154-155`），并追加 `TASK_DELETED` |
| 停止规则 | `RepeatActions.kt:128-146` | 模板 `kind="已停止重复"`、`repeatPaused=true`（`:133`）；待处理实例（谓词 `:130` = `repeatTemplateId == template.id && kind == "任务" && !it.done`）改为 `kind="重复历史"`，`detail` 为 `"本次未处理"` 或 `"规则停止，取消本次"`（`:134-135`），并清空 `scheduledAt`/`dayOnly`/`windowStartAt`/`windowEndAt` |

**【实测】关键点**：`deleteRule` 只保存了**模板自身**的快照；被 `stop` 改动的实例**没有**任何字段记录归属。而事后无法从项状态还原该集合：

- `stop` 的谓词（`RepeatActions.kt:130`）与 `pause` 的谓词（`RepeatActions.kt:109-110`）**逐字相同**；
- 三种操作（`stop`/`pause`/`cancelInstance`）在「错过」分支写入的项状态**完全同形**（`kind="重复历史"`、`detail="本次未处理"`、`scheduledAt=null`）；
- 仓库现有消费者 `app/src/main/java/com/sakata/focusflow/RepeatHistorySummary.kt:24-35` 正是按 `detail` 字符串分类（`:28-34`），不做时间对齐；
- 事件日志可**部分**重建：非 missed 实例有 `TASK_UNSCHEDULED` 的 `extra` 区分（`"停止重复"`/`"暂停重复"`/`"取消重复本次"`，分别在 `RepeatActions.kt:144`/`:123`/`:184`），但 missed 实例的 `REPEAT_MISSED` 三处**都没有 extra**（`:141-142`/`:120-121`/`:181-182`），只能靠与同模板 `REPEAT_RULE_CHANGED`（extra `"停止"`，`:139-140`）的 `recordedAt` 对齐来间接归因。**代码里没有任何执行这种重建的函数。**

### 2.2 `deleteRule` 会把模板状态整体还原

**【实测】** `stop` 无条件把模板设为 `repeatPaused=true`（`RepeatActions.kt:133`），而 `deleteRule` 的快照编码的是**调用前**的原始 `template`（`:155`），不是 `stopped` 之后的模板。因此快照里的 `repeatPaused` 是**删除前**的值：

- 若删除前规则在运行 → 快照 `repeatPaused=false`，恢复后规则继续生成；
- 若删除前用户**手动暂停**过 → `pause` 已把 live 项的 `repeatPaused` 置 true（`RepeatActions.kt:113`），快照带上 `true` → 恢复后仍是暂停；
- 第三种情形（先「停止」再删除）**在 UI 上不可达**：`stop` 后 `kind="已停止重复"`，而删除按钮只在 `kind=="重复模板"` 时渲染（`TodoUi.kt:217`）；程序化再调 `deleteRule` 也会被 `stop` 的守卫拦下（`RepeatActions.kt:129`）并返回空事件。

## 4. 待决三项

### 决策 A —— 恢复重复规则时，恢复范围取哪一档？

**背景**：见 2.1。`deleteRule` 把待处理实例转成「重复历史」并清空时间；当前恢复路径 `TrashActions.restore`（`app/src/main/java/com/sakata/focusflow/TrashActions.kt:22-34`）只按 `trashSnapshot` 还原**模板**，实例停在历史态。

**选项**

- **A1 只恢复模板**：实例保持「重复历史」。用户看到「规则回来了、下一个实例是新的」，原来的实例不回来。实现最简单，组负载只需 `templateSnapshot`。
- **A2 同时恢复受影响的未来实例**：需要新增记录——删除时必须把被 `stop` 改动的实例逐个存快照（ID + 删除前完整 `Item` + 删除前 `kind`/`detail`/`scheduledAt`）。恢复时按 ID 精确匹配还原，**禁止**用「凡同模板的历史项」或「同名」扩大范围。
- **A3 两档都由用户选**（恢复时提供选择）：契约与界面都要分叉。

**影响面（请重点评估）**

1. **组负载形状**：A1 只存模板；A2/A3 必须存 `affectedInstances` 数组。这决定 `RepeatJournal` 组记录的结构与迁移。
2. **时间策略**：若某实例的旧 `scheduledAt` 在恢复时**已过期**，该不该还原成待办？设计全文的拟议（§4.1.1）是：未来实例还原，过期实例保持历史、**不**补发提醒（对齐 7.3 交接件「恢复只重排有效的未来提醒」），且**不因存在过期实例而拒绝整组**。
3. **`class_day` 规则的课程变更**：若该日课程已不再命中，拟议不还原为待办。
4. **与 2.2 的交互**：恢复模板时若快照带 `repeatPaused=true`（删除前已暂停），按 A2 还原实例会不会与「规则仍暂停」冲突？需要明确「暂停中的规则是否还恢复实例」。

**供判读的具体用例**（可作为验收断言）

- 每日规则、1 个未完成未来实例：删除 → 模板进回收站且该实例变历史（`scheduledAt=null`）→ 恢复 → ？实例应否回到 `kind="任务"` 且时间等于删除前。
- 同一规则下另有 1 个**已 `done`** 的实例与 2 个早已转历史的实例：恢复时**不得**被纳入。

### 决策 B —— 删除前规则处于「暂停」时，恢复后是否保留暂停意图？

**背景**：见 2.2。快照天然带的是**删除前**的 `repeatPaused`。

**选项**

- **B1 还原删除前状态**（快照忠实还原）：删除前暂停 → 恢复后仍暂停，不自动生成实例。语义一致，用户不会被意外“复活”一条自己停过的规则。
- **B2 无条件恢复为可继续生成**（清 `repeatPaused`）：用户点“恢复”的直觉可能是“让规则继续”。

**影响面**

- 决定恢复后模板的 `repeatPaused` 落什么值，以及是否立即触发实例生成。注意 `RepeatActions.refresh` 的模板过滤器要求 `!it.repeatPaused`（`RepeatActions.kt:44`），所以 B1 下**不会**生成实例，B2 下会。
- 与决策 A 的交互：若取 A2 且 B1（暂停），实例该不该一并还原？
- 已排除的第三种情形：先「停止」再删除（UI 不可达，见 2.2），不需要为它设计。

### 决策 C（= 设计全文的 U19）—— 重复规则是否接受 30 天自动永久删除？

**背景**：现状下重复规则墓碑**没有** `expiresAt`、不属于任何组，因此**永不到期**，只能被手动永久清除（2.3 表）。7.4 一旦为它建立组并写入 `expiresAt`，其成员就会落入 7.3 既有的定时清扫 `expiredIds`（`8a3c96b` 的 `data/TrashJournal.kt:145-156`）。

**选项**

- **C1 接受收紧**：重复规则与普通条目同寿命（30 天）。优点是规则统一、界面可统一显示「剩余保留期」；风险是**用户可能失去一条长期不用但仍有价值的重复规则**，且这是相对现状的行为收紧。
- **C2 让 `expiredIds` 跳过重复规则组**：重复规则**不过期**，只支持手动永久清除（与其「可长期保留的规则」语义更接近）。需要 7.4 与 7.3 约定该种类不参与定时清扫。

**影响面**

- 直接决定 `repeat_rule_closure` 是否要写 `expiresAt`，以及测试 R5/R20 的预期。
- 若取 C1，删除确认与回收站界面必须**明示**「30 天后自动清除」，否则违背设计约定「界面不得提前承诺未实现的自动清理」的反向要求（不得静默引入自动删除）。
- 注意 7.3 已把 `expiredIds` 的边界冻结为 `now >= expiresAt` 到期、`now == expiresAt - 1` 不到期，7.4 不应另立口径。
