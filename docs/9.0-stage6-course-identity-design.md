## 1. 现状与必须先解决的阻断点

1. `ZjuTimetableClient.fetch` 以所选学年 `year.value`、学期 `term.value` 请求接口，成功时返回 `year.text`、`termDisplay`；`ZjuTimetableImportActivity` 将这两项显示文本传给 `MainActivity`，后者仅把 `payload` 传给 `ZjuTimetableParser.parse(payload)`。因此当前没有可追溯的原始学年/学期**请求代码**进入 `CourseImportBatch`。
2. `ZjuTimetableParser` 只从 `kbList` 取课程名称、星期、节次、地点和单双周提示。仓库测试使用自造 JSON，仅含 `xqj`、`djj`、`skcd`、`jcs`、`dsz`、`kcb`、`kcmc`、`cdmc`；没有真实且脱敏的返回行，不能断言教学班号、课程号或稳定行号究竟存在、叫何名字、是否跨次导入稳定。不得凭常见教务字段名硬编码。
3. `CourseImportPolicy.prepare` 用星期＋起止节次＋标题 `distinctBy`，会抹去来源、班级及地点差异；`syncSchoolCourses` 可按标题、星期和节次或唯一同日标题更新旧记录。两者在有同名不同班时不足以保证身份正确。更换导入契约时必须同步修订其测试与去重策略，保留未证明同一性的候选行。
4. 旧 `Course` 就是一条课次，`Course.id` 同时为通知 PendingIntent、持久去重、课次提醒覆盖、临时地点和 UI 的键。初次 Room 迁移生成 `CourseEntity(id=旧 id)`＋`CourseMeetingRuleEntity(id=旧 id, courseId=旧 id)`。`RoomCoreDataReadRepository` 以两表等长、同序且 `parent.id == rule.id` 验证，并 `zip` 投影；`toLegacy(parent)` 又使用父 ID。`RoomCoreDataWriteRepository.replaceCourses` 也强制一对一。任何直接插入第二条子规则的尝试都可能被读路径判为无效，或使两个课次共享 ID。现有 Room schema 为 v5，产品激活仍关闭。
5. 真实旧数据的生效日期、确认状态、用户启停和提醒偏好必须保留。阶段 2 审计确立“旧数据先一对一、不按同名归并”；本设计沿用这一边界。

## 2. 字段契约：每条导入行与课次一一对应

先引入一个**仅内存的规范化候选行**，保持与原始 `kbList` 行的索引对应；禁止将元信息作为与 `List<Course>` 平行且会被过滤打乱的列表。字段命名是内部语义，真实 JSON 键需要证据确认。

| 字段 | 规则 | 缺失时 |
| --- | --- | --- |
| `source`、`institution` | 来源限定为浙江大学教务；手动/截图/其他学校绝不参与教务自动匹配 | 拒绝以官方身份同步 |
| `schoolYearCode`、`termCode` | 保留实际请求的原始选项值，同时可另存显示文本；整个批次内一致。不可把“秋/冬”等显示文字当唯一键，也不可未经取证裁剪 `xqm` 的值 | 阻断自动匹配；课程仍可作为待确认候选 |
| `externalTeachingClassId` | 经真实样本核对、证明确为**教学班稳定标识**后才作为同课程聚合依据；课程号可作为辅助校验，但同课程号的不同教学班不得合并 | 每条时段独立候选，按旧导入入口保守处理 |
| `externalCourseCode` | 可选佐证；不单独作为聚合键；与已保存班级身份冲突时阻断自动更新 | 不改变已知教学班归属 |
| `externalMeetingId` | 仅当真实行中有可证明稳定的每课次标识时使用。课次改星期/节次/地点后仍须保留内部 `meetingId` | 只能进行唯一且无歧义的旧新课次匹配；歧义保留待确认，不替换旧课次 |
| `weekday`、`startPeriod`、`endPeriod`、`building`、生效范围／单双周 | 校验合法范围；地点和时间是可变内容，不能代替稳定身份；无法表达的单双周/不连续周次保持待确认并提示 | 无效行跳过并计数；不得覆盖原记录 |
| `sourceRowIndex`、`sourceOrder` | 保留本批原始行索引及页面顺序，用于溯源、诊断和显示；不当跨次导入的唯一键 | 记录不可自动更新 |

只有经过真实取证验证的 `(source, institution, schoolYearCode, termCode, externalTeachingClassId)` 才构成**课程父记录**的外部匹配键；同一个键若对应相互冲突的课程号、标题、班级或多种不可解释的行标识，停止自动归并。课次 ID 始终是 app 自己的正整数唯一 ID；外部编号不可直接写入 `Course.id`。

## 3. 旧用户数据与一对多边界

1. **初次迁移保持一对一**：每条旧 `Course.id` 原样成为 `CourseMeetingRuleEntity.id`；保留旧来源顺序、确认/启停、生效范围、星期节次和地点；其 `CourseEntity.id` 也沿用旧 ID。未知来源或缺少教学班证据的同名记录继续作为不同父记录。对已存在 Room v5 数据必须提供显式 v5→v6（版本号仅为示意，按实际 schema 定）升级及旧库无损验证，不能依赖破坏性重建。
2. **经证明同一教学班后再归组**：课程父 ID 为 app 内部分配、跨重导入稳定的 ID；首次把几条既有课次归组时可明确选一条旧父 ID 作锚并记录其他父 ID→新父 ID 的可追踪映射，所有原课次 ID 原样保留。新建课次从不重用现有 ID。缺号、跨学期、同名异班、同号矛盾和人工拆分过的归属都不自动归组；人工合并/拆分属于下一组检查点。
3. **先改完整投影再允许多规则写入**：Room DAO 按 `course_id` 关联父记录、按 `source_order,id` 排序；校验父 ID 唯一、课次 ID 正且唯一、每个课次恰有父记录、无孤儿、字段合法，允许父数小于课次数。`CourseMeetingRuleEntity.toLegacy(parent)` 必须用 `rule.id` 构造旧 `Course.id`；`RoomCoreDataReadRepository` 不再等长 `zip`。读写仓库、启动影子比较与测试 fixture 同步支持一对多，未全部支持前不写入一对多数据。
4. **提醒与地点跟课次走**：`CourseReminders` 的 `meeting_{id}`、`delivered_{id}`，`CourseLocationOverrides` 的 `{meetingId}_{epochDay}`，PendingIntent 和通知标签，全部保留原 `meetingId`。总开关保持默认关。父记录归组不得把任一课次覆盖复制到全课程，也不得合并不同课次的送达标记；新增课次按现有总开关及课次覆盖语义处理。若未来提供“整门课程提醒开关”，需独立产品决策和新键，不复用旧键。
5. **旧 JSON 与 Room 的一致性**：运行时仍以 Legacy 为产品源，旧格式继续存一条课次一条记录。多课次归组需有能在旧快照和 Room 影子比较中稳定还原的父关联；跨 SharedPreferences 和 Room 没有单一事务，不能声称 `saveCourses` 与新身份映射同时原子提交。任何写入设计须先给出保存前旧快照/映射备份、提交顺序、掉电中断恢复与不一致阻断规则；未验证前仅收集/展示候选，不改变已确认课次或打开 Room 激活。

## 4. 导入判定与失败处理

| 输入情形 | 处理边界 |
| --- | --- |
| 同一学期、同一可信教学班号、多行课次；每行能唯一对应课次 | 仅在持久关联与读写投影全部就绪后组成一门多课次；原 ID/提醒/地点逐条保留 |
| 同名但不同教学班号／不同学期／不同来源 | 不自动归并，保留独立候选和明确来源 |
| 缺班级号、班级号在一次批次中冲突、同号配不同课程号 | 不覆盖已确认用户课次；记录待确认及原因 |
| 教务重导入时某行缺失、节次被改、地点被改、单双周无法表达 | 缺失不自动删除；可信课次 ID 或唯一映射才能保留原 ID 更新，否则待人工确认；待确认新行不建立提醒 |
| 数据校验失败、存储提交失败或快照已变化 | 保留原课程与偏好，停止调度新课次，报告明确可重试的错误；绝不清空/重建用户数据 |

当前 `syncSchoolCourses` 的按标题匹配行为仍属于旧实现；在启用新身份契约前必须通过显式入口/策略隔离，不能把旧启发式结果称作“稳定身份”。

## 5. 验证门槛与可交 DeepSeek Flash 的首项任务
