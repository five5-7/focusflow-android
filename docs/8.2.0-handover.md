### 必读的坑：git 要带 `safe.directory`

本机 Windows 用户 SID 与仓库属主不一致，直接 `git ...` 会报
`fatal: detected dubious ownership`。所有 git 命令都要加前缀：

```powershell
git -c safe.directory=D:/focusflow/focusflow-android-8.0.0 -C D:\focusflow\focusflow-android-8.0.0 status
```

写入 `~/.gitconfig` 需要提到工作区外权限，直接带 `-c` 最省事。

## 七、踩过的坑（省时间用）

1. **`.ps1` 里有中文且没有 BOM → PowerShell 5.1 会乱码并解析失败。** 工具脚本一律 ASCII-only；
   要写中文用 `[System.IO.File]::WriteAllText($p, $s, (New-Object System.Text.UTF8Encoding($false)))`。
   中文界面文案放进 `patterns.txt` 用编号引用。
2. `.NET` 的工作目录与 PowerShell 的 `cd` 不一致 → 脚本里用**绝对路径**。
3. Gradle daemon 会抓住调用者的管道不放 → `build.ps1` 里是在 `cmd /c` 内重定向到日志文件的，别改。
4. `Get-CimInstance Win32_Process` 被沙箱拒绝；`npm view` 需要 `--cache D:\focusflow\.tmp\npmcache`。
5. `uiautomator dump` 时好时坏，读开关状态不可靠——不要用 dump 判断 Switch 状态。
6. `Compose` 的 `lerp(Color, Color, Float)` 是**分量级 sRGB 插值**（真机实测过），不是线性空间。
7. `Modifier.background(Brush)` 的渐变**跨元素自身高度**——这正是「跟随内容」的实现依据。
8. 转场透明是踩过的老坑：副页每个动画层都必须有**不透明**背景（`pageLayerBackground`），
   开启渐变/跟随内容时也不能破例（提交 `e4d54ea` 就是补这个）。
9. **`function X { param([string[]]$Args) ... $y = & $tool @Args }` 一定不要这么写。**
   `$Args` 是 PowerShell 的自动参数，用它当形参名会让 `@Args` splat 失效：命令收不到任何参数，
   `adb` 于是打印一大段 help、**退出码仍是 0**，后面的 `uiautomator dump` / `pull` 全部没执行，
   脚本继续读**上一次留下的 XML** 并据此报告页面状态。症状是"脚本说得头头是道，但全是假的"，
   2026-09-10 为此丢了近一小时。改用 `param([string[]]$AdbArgs)` + `@AdbArgs`。
   配套口径：先删本地 dump 再拉，拉不到就返回空串报错，**绝不**回退读旧文件。
10. **`uiautomator dump` 会冻结 UI 大约 2–5 秒，紧接着发的 `input tap` 有时会被丢掉。**
   所以脚本里"dump → 按坐标点一下 → 认为已经跳转"是不可靠的；每一步点完都要**重新 dump 验证页面**
   （`reset_appearance.ps1` 的 `Open-Appearance` 就是带重试的写法，最多 3 轮）。
11. **`$ErrorActionPreference = "Stop"` 与 adb 不兼容**：adb 把 daemon 启动横幅和传输进度写在
   stderr，`Stop` 会让每一条都变成终止错误。用 `Continue`，再靠"校验每步输出"来发现真正的失败。
12. 判断"页面到底在哪"不要只看一个关键词：**今日页的 dump 里也含"深色模式"**。
   外观页要同时含 `页面背景` + `深色模式`。
13. 读 `adb` 抓下来的 XML 别用 `Get-Content -Raw`（中文会变乱码）；
   用 `[System.Text.Encoding]::UTF8.GetString([System.IO.File]::ReadAllBytes($p))`。
14. **主题行与卡片材质的可读性不一样**：主题行的选中态会渲染一个 `已选择` 文本节点，能从 dump 读出来
   （"已选择"前面最近的那个主题名就是当前主题）；而 `默认/渐变/柔光/纸感` 四个 FilterChip
   只靠填充色区分，dump 里四个都是 `selected="false"`，**读不出来**，别浪费时间去解析。
15. **内置主题的 label 不等于它的名字**：`OCEAN` 的 label 是 **海盐蓝**（不是"海洋"），
   `MINT` 是"薄荷绿"。脚本里按 label 找行，写错就永远找不到、静默跳过（第 9 条的同类事故）。
16. **设备不是干净的**：`.tmp` 里大量真机试验会留下非默认外观（2026-09-10 19:00 实测残留
   `主题渐变 200%` + `薄荷绿`）。跑不变量比对**之前**先跑
   `powershell -File D:\focusflow\.tmp\reset_appearance.ps1` 把主题/背景/材质复位到 8.1.1 的样子，
   否则会拿到假差异。

### 弹窗 / 底栏材质为什么一直不渲染（本轮查清，根因只有一个）

**`Modifier.drawBehind` 排在 Material3 `Surface` 内部 `.background(color)` 之前。**
把 `surfaceMaterialFill` 挂在 `Surface(modifier = …)` 上时，画出来的材质层会被 Surface
自己的**不透明底色整块盖住** —— 从外面看就是"这个控件没有材质渲染"。

- `FocusCard` 一直正常，只是因为它恰好把 Surface 底色设成了 `Transparent` 再在内容里画材质；
- `AppDialog`（维护者连报两次的「弹窗还是没有渲染」）与 `FloatingNavigationBar`
  （"材质也影响导航栏"）都踩了这个坑，**从加材质那天起就没显示过**。

修法与验证：

| 位置 | 修法 | 真机证据 |
|---|---|---|
| `AppDialog` | 材质层改成画在 Surface **内容**里最底层的一个 `matchParentSize()` Box | 弹窗卡面 x=1220：y=1250 `rgb(225,235,230)` → y=2200 `rgb(243,250,246)`，**+18 级竖向渐变**（修前是纯平） |
| `FloatingNavigationBar` | `color` 在"有画刷 **或** 材质非默认"时让成 `Transparent`；`surfaceMaterialFill` 自己先铺一层底色，所以不会留洞 | 底栏 x=640：栏顶 `rgb(218,228,223)` → 栏底 `rgb(232,242,237)`，**+14 级** |

**判定口径**：`surfaceMaterialFill` 在材质为默认(TONAL)时**什么都不画**并原样返回 `this`，
所以两处的 `color` 都必须在 TONAL 时保持不透明 —— 默认外观逐像素不变量因此不受影响。

### 流畅度：实测结论是「与材质无关」

维护者反馈「这几个版本流畅度似乎有问题」，用 `framestats.ps1` 做了同一台机器的 A/B：

| 场景 | 默认材质 tonal | 柔光 soft | 记录基线 |
|---|---|---|---|
| 页签切换 | 2.65% / p90 14ms / **p99 77ms** | 2.38% / p90 16ms / p99 73ms | 2.23% / p99 40ms |
| 长列表滚动 | 0.29% / p99 11ms | 0.44% / p99 12ms | 0.44% |
| 弹窗开合 | 3.35% / p99 53ms | 2.38% / p99 57ms | 3.72% |
| 副页转场 | 3.19% / **p99 117ms** | 2.48% / **p99 117ms** | 2.47% / p99 61ms |

- **重帧率全部在 5% 预算内**，且两组互有胜负 → 材质不是瓶颈；
- 真正变差的是 **p99（偶发长帧）**，而且**默认材质下同样是 117ms**，所以它跟材质无关；
  最可能是"设置 → 外观"这类重页面**首次组合**的成本（那一页有十几组 chip 与七套预设）。
- 顺手修掉一个**确实存在**的每帧开销：`materialBrush` 原先建在 `drawBehind` 的 lambda 里，
  **每一帧、每一张卡片**都会新建一次渐变 Brush 并重编 shader；

**T-1 柔光与纸感现在完全一样（最高优先，因为它同时暴露两个缺陷）**
- 现象（维护者实测）：柔光与纸感渲染**完全相同**，都是同一张变向渐变。
- 已查明原因（两层，都要修）：
  1. 纸纹改成了中性灰 + `BlendMode.Overlay`。而 **Overlay 在接近纯白/纯黑的底色上效果趋近于零**
     （`base=0.98` 时 ±28 灰阶偏差只剩约 **2 灰阶**）→ 近白卡片上纸纹等于不可见。
     这是**技术选择错误**：纸纹本身可行，但 Overlay 不适合近白底。
     正解方向：成对的"暗点 + 同量亮点"像素让平均亮度守恒，或改用
     `BlendMode.SoftLight` / 极淡的乘性暗点配合补偿。**必须同时满足"近白底可见"与"亮度中性"。**
  2. 柔光本身也**不是亮度中性的**：顶站 +9% 白、底站 −5% onSurface。近白卡片"往白里混"没有空间、
     往深里混却很明显，实测卡面 `251.3 → 241.3`（底色约 250）→ **净暗 4 灰阶**，
     看起来就是"曲线反了"。与纸纹同类，应改成亮度守恒的画法。
- 维护者还问过"是不是没做"——**要如实回答：做了，但被这两层缺陷抵消/掩盖了。**

**T-2 卡片的渐变提供「上→下」「下→上」两个方向**
- 现在卡面只有一种方向（`softLightStops` 固定顶亮底沉）。

  页面是 6 档（含斜向与横向），卡片按维护者口径只要**两个竖直方向**。
- 需要新偏好键（例如 `appearance_card_gradient_direction`），默认 = 现状（上→下），
  老装机读不到即不变。别复用 `gradientDirection`（那会顺手把页面的斜向也套到卡片上）。

**T-3 通知栏遮罩"直接切割"太生硬（这一轮刚引入的，观感回退）**
