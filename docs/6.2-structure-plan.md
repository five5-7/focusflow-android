# FocusFlow 6.2 结构重整计划

状态：阶段 A–D 已完成；阶段 E 仅待 OPPO / ColorOS 16 真机验收

基线：`agent/focusflow-6.1-reminders` / `9ca8ca2`  
开发分支：`agent/focusflow-6.2-structure`  
目标版本：`6.2.0`（versionCode 462）

## 1. 为什么现在重整

FocusFlow 已具备记录、日程、课表、目标、提醒、饭点、通勤、地点、教程和 AI 等能力，但功能增长快于日常使用路径的收敛，产生了两个问题：

1. 用户每天面对的入口过多，低频功能与高频动作争夺注意力。
2. 代码集中度过高：`MainActivity.kt` 约 5233 行，`PrototypeStore.kt` 约 1000 行，页面、状态、持久化和提醒调度之间耦合明显。

6.2 不继续增加大型能力，重点是让已有能力更容易找到、更少打扰、更容易维护。

## 2. 产品目标

### 2.1 每日核心闭环

默认界面只强化以下路径：

`快速记录 → 收集箱 → 安排到日程 → 提醒 → 完成 / 推迟 → 保留记录`

### 2.2 信息架构

底部导航维持四个入口和中央加号，降低迁移成本：

| 入口 | 默认内容 | 按需内容 |
|---|---|---|
| 今日 | 下一件事、今日概览、收集箱、当前活动 | 饭点、精力、睡前减速；有数据或启用后出现 |
| 日程 | 日视图、周视图、已完成灰化任务 | 课程色块；有课表后出现 |
| 计划 | 目标与待安排事项 | 课表与空挡、复盘、资料工具箱，使用堆叠条目进入副页面 |
| 设置 | 通知与权限、外观、数据 | 校园、地点、通勤、AI、应用检测等高级设置 |
| ＋ | 快速记录 | 安排活动等次级动作 |

规则：

- 不为每个功能增加独立开关。
- 有明确后台行为、权限或通知影响的功能保留开关。
- 纯展示功能通过“有数据才出现”或收进副页面处理。
- 页面返回时保持用户位置；每次重新进入“计划”时条目默认折叠。

## 3. 功能取舍

### 3.1 保持在主流程

- 收集箱的记录、编辑、删除、安排时间。
- 日/周日程和任务完成、改期、删除。
- 下一件合适的事，但只输出一个可执行建议并说明原因。
- 通知权限检测、日程提醒、饭点忽略与跨日恢复。

### 3.2 条件显示

- 饭点：完成习惯基线或存在饭点记录后显示。
- 课程：存在已确认或待确认课程后显示。
- 空挡：存在课程或自由时段数据后显示。
- 校园能力：生活阶段为“上学”且校园生活已启用时显示。
- 目标提示：存在目标或待安排目标任务时显示。

### 3.3 收进工具箱

- 教程搜索、视频分析、AI 周总结。
- 地点包、地图导入、通勤校准。
- 前台应用检测与应用分类。
- 习惯原始事件查看、实验性统计。

### 3.4 教程改为“执行依据”

当前“搜索建议 → 保存为教程 → 全局当前标准”的链路停止扩展。6.2 改为：

- 资料库只保存用户确认过的真实链接、笔记或材料。
- 每个目标独立关联资料，不再默认共用全局标准。
- 目标分别保存“本次先做什么”和“完成标准”。
- AI 只负责把已选资料整理成候选行动，用户确认后才写入目标。
- 没有资料也能创建和执行目标。

旧数据兼容：保留现有教程与目标关联；旧“当前标准”只作为资料库标记展示，不再自动应用到新目标。

## 4. 代码结构目标

采用渐进式拆分，不一次性引入大型框架或数据库迁移。

```text
com.sakata.focusflow
├── app/
│   ├── FocusFlowApp.kt
│   └── FocusFlowNav.kt
├── core/
│   ├── model/
│   ├── time/
│   └── ui/
├── data/
│   ├── FocusFlowRepository.kt
│   ├── PreferencesDataSource.kt
│   └── migration/
├── feature/
│   ├── today/
│   ├── schedule/
│   ├── plan/
│   ├── settings/
│   ├── capture/
│   └── guidance/
└── reminders/
    ├── ReminderScheduler.kt
    ├── ReminderReceiver.kt
    └── ReminderPolicy.kt
```

约束：

- Composable 只负责展示与产生 UI 事件，不直接拼接持久化流程。
- 页面状态由页面级 state holder / ViewModel 管理；不在根 Composable 堆放所有对话框状态。
- `PrototypeStore` 先拆接口和领域仓库，底层 SharedPreferences 格式暂时保持，避免用户数据丢失。
- 时间计算、建议排序、通知决策保持为纯 Kotlin 逻辑，便于单元测试。
- 接收器不自行推断产品状态，只调用提醒策略与仓库。

## 5. 分阶段实施

### 阶段 A：建立安全网

- 记录 6.1 数据键与 JSON 格式，补读取旧数据的回归测试。
- 为导航状态、条件显示和教程迁移增加纯逻辑测试。
- CI 继续执行单元测试和稳定签名 APK 构建；失败时不提供测试包。

验收：旧版本数据载入后，任务、课程、目标、饭点记录和设置数量一致。

### 阶段 B：拆代码，不改行为

- 从 `MainActivity.kt` 提取四个页面、通用时间轴、对话框和导航壳。
- 将模型从界面文件移动至 `core/model` 或对应 feature。
- 为 `PrototypeStore` 增加仓库接口，先由现有 SharedPreferences 实现。

验收：界面与 6.1 行为一致；单个页面文件尽量控制在 800 行以内，根 App 只负责导航与全局事件。

### 阶段 C：重叠页面

- 今日页按“现在 → 接下来 → 收集箱 → 条件模块”排列。
- 日程页保留日/周视图，课程和完成任务在同一时间轴呈现。
- 计划页只显示堆叠入口；课表、空挡、目标、复盘、工具箱进入副页面。
- 设置首页只保留高频设置，其余进入高级工具副页面。

验收：首次安装不配置任何高级功能时，主流程没有空白大卡片；完成一次快速记录到安排不超过三次点击。

实施结果（2026-08-25）：

- 今日页已按“现在 → 接下来 → 收集箱 → 条件模块”重排，并接入统一显示策略。
- 日/周时间轴继续共用任务与课程布局，完成项保留灰化；周视图无需横向滚动。
- 计划主页保持堆叠入口，资料、视频与 AI 能力移入独立“资料工具箱”。
- 设置主页保留外观、提醒、作息等高频设置；地点、AI、课表识别、应用检测、稳定性、原始习惯事件与可选消费汇总进入“高级工具”。
- 新增阶段 C 信息架构单元测试，锁定首次安装无可选模块空卡、核心模块顺序与三次点击上限。

### 阶段 D：教程降级与执行依据

- 删除“保存搜索词即设为全局标准”的自动行为。
- 目标编辑器允许选择资料、填写第一步动作和完成标准。
- 已安排任务携带该目标自己的执行依据。
- AI 与视频分析移入工具箱，保存前必须确认实际资料或行动。

验收：两个目标可关联不同资料；不添加资料也能正常创建、安排和完成。

实施结果（2026-08-25）：

- 目标新增兼容字段 `firstAction`，旧 JSON 缺失时读取为空，不迁移或覆盖旧数据。
- 新建和已有目标均可编辑自己的第一步、完成标准、资料与章节；安排任务时复制该目标自己的执行依据。
- 资料库旧 `selected` 字段降级为“常用标记”，不再默认关联新目标，也移除批量应用行为。
- AI 搜索建议只能作为候选第一步，不能直接生成教程；资料和视频必须包含用户确认的链接、材料或笔记才可保存。
- 两个目标独立资料、旧数据读取与任务执行详情均有纯 Kotlin 回归测试。

### 阶段 E：真机验收与发布

- CI 生成稳定签名 `FocusFlow-6.2.0.apk`。
- OPPO / ColorOS 16 验证通知权限、饭点忽略、任务提醒、重启恢复和后台限制。
- 连续使用 7–10 天后再决定删除、保留或提升低频功能，不以页面开关数量作为完成标准。

## 6. 不在 6.2 范围内

- 自动地图地点识别和后台定位扩展。
- 通勤时间的无确认自动学习。
- 饭点消费与理财联动。
- 新的第三方服务或新的 AI 模型能力。
- 全面迁移 Room、依赖注入框架或多模块 Gradle；除非渐进拆分证明现有存储已成为阻碍。

这些能力保留在后续路线图，避免结构重整期间同时改变产品行为、数据格式和外部依赖。

## 8. 提交与回滚策略

- 每个阶段独立提交，先拆分再改行为，不混在同一提交。
- 6.2 以独立分支和 PR 交付，不直接修改 `main`。
- 每阶段保持可构建；若页面重组效果不理想，可回退对应行为提交而保留结构拆分。
- 未经确认不合并；真机测试只使用 CI 的稳定签名 APK。
