## 2. 组②为什么不能直接照组①的方式推进

组①的自动归并至今**未放行**（review3：`xkkh` 只被允许作为"同一请求学年＋学期内的候选分组键"进入只读设计与内存预览）。
组②换了一条路：**把判断权交给用户**——系统只标出"看起来是同一门课"的候选组，由用户手动决定合并／拆分。
因此组②**不依赖**组①那批仍缺的真实证据（`xkkh` 跨课表变更的稳定性、同名异班反例），可以在只读预览之上独立开工。

## 3. 现有数据契约（决定了难点在哪）

| 事实 | 位置 | 对组②的含义 |
|---|---|---|
| `Course.id: Long` 是稳定身份 | `CourseSchedule.kt:3-15` | 合并必须回答"**谁的 id 活下来**"，其余记录的 id 会消失 |
| 临时地点覆盖按 **`(course.id, epochDay)`** 存储 | `CourseReminders.kt:146-147`（`CourseLocationOverrides`） | 被合并掉的 id 会让**已存在的临时地点覆盖变成孤儿**——必须迁移或明确告知用户 |
| 提醒覆盖按课程存储 | `CourseReminders.kt:48`（`course_reminder_settings`） | 同上：合并前要合并两侧的覆盖值，冲突要有确定规则 |
| 生效期已是字段 | `Course.effectiveFromEpochDay` / `effectiveUntilEpochDay` | "该时段后续"这类编辑范围**已有落点**，不需要新字段 |
| 相邻时段只是**显示**合并 | `CourseDisplayGroups.kt`、`CourseTimetableUi.kt:209`（"相邻时段已合并显示；每段仍可分别编辑"） | 显示合并 ≠ 记录合并；组②不得改变显示分组语义 |
| 组①只读预览已落地 | `CourseIdentityPreview.kt`（无写入路径调用） | 组②的候选来源就是它，不能反过来让它承担写入 |

## 4. 范围：三件事，按顺序

### 4.1 编辑范围（先做，风险最低）
把"编辑这门课的某个属性"分成三种作用域，映射到**已有机制**：

| 作用域 | 语义 | 用现有机制如何表达 | 需不需要新建记录 |
|---|---|---|---|
| **单次** | 只改某一天的那次课 | `CourseLocationOverrides`（已是按 `(id, epochDay)`） | 不需要 |
| **该时段后续** | 从某天起改，之前不动 | 把原记录 `effectiveUntilEpochDay` 收在该天之前，新建一条 `effectiveFromEpochDay` = 该天 | **需要**（新 id） |
| **整门课程** | 改这门课的定义 | 直接改记录 | 不需要 |

### 4.2 拆分（在 4.1 之上）
"该时段后续"本质上就是拆分。因此 4.1 做对了，拆分不需要第二套机制。

### 4.3 合并（最后做，风险最高）
两条以上记录合并成一条。**必须先把下面三件事定死**，否则会毁用户数据。
以下三条已由用户于 **2026-09-29 确认定稿**（不再是"建议"），纯函数与单测直接据此实现：

1. **id 存活规则（定稿）**：保留 **`id` 最小者**（确定性、与用户操作顺序无关），其余 id 作废。
2. **孤儿覆盖的处置（定稿）**：作废 id 上的 `CourseLocationOverrides` 与提醒覆盖**必须迁移**到存活 id；
   同一天两侧都有值时，**用户正在操作的那条优先**，其余按 id 升序并入；迁移条数要**展示给用户**
   （代码实际输出的原句是"已从被删除的记录迁移 N 天本次地点。"）。计数口径（逐天判定，修过一轮阻断级缺陷后定稿）：
   - `migrated` = 结果里该天来自**被删除**记录、且存活记录本来**没有**这一天（纯"带过来"）；
   - `superseded` = 存活记录本来有这一天、且另有记录也有 ⇒ **必有值被丢弃**；
   - `overwrittenSurvivor` = 存活记录本来有这一天，但最终胜者**不是**它 ⇒ 用户必须知道自己的值被换了，
     确认文案要写出来（配合项：胜者按**写入顺序**判定：优先记录有该天则它胜，否则 id 最大者胜）。

   **三者的关系（不要说成"互斥且穷尽"——已被反例否证）**：`migrated` 与 `superseded` 以"存活记录本来有没有这一天"
   划分，**两者互斥**；`overwrittenSurvivor` 是**叠加的警示口径**，可以与 `superseded` 在同一天同时成立；
   只有存活记录持有某天时，三个数都不动（没有值被丢弃）。

   原先的 `superseded = |被删除天 ∩ 优先天|` 从未验证"值真被丢弃"，会把只有优先记录拥有的天也算进去（多算）。
   另一处已知的可观测性缺口（照登）：当存活记录**没有**某天、而两条被删除记录都有该天时，只有胜者的值进入结果，
   落败的那条被丢弃却**没有任何计数器或文案**指向它。

3. **不可逆性（定稿）**：合并**先不支持撤销**，但确认文案必须写明"将删除 N 条记录"，并显式写出"合并不支持撤销"。
   将来若做撤销，留给下一个检查点。

**字段取舍（实现方默认，与第 2 条同源）**：可编辑字段取**用户正在操作的那条**（标题为空则取 id 最小的非空标题）；
只有**相同星期与节次、且生效期相连或重叠**的旧记录才可拟成一条；不同课次需先有一对多的课程模型，
不相连的生效段也不能用一条连续记录表示。对这两类输入，纯计划返回拒绝，不产出可供接线写入的删除计划。
在可安全表示的输入中，生效期取连续并集，且**空值 = 无边界**（任一记录该端为空 ⇒ 结果该端为空）。

> 这条语义是被一轮**阻断级**复核逼出来的：原实现用 `mapNotNull{}.min()/max()` 丢弃 null，
> 会把默认课程 `(null, null)` 拆分后再合并成 `(150, 149)` 这种**倒置区间**；而
> `CourseActivationPolicy.isActiveOn` 要求 `from <= 当天 <= until` ⇒ 整门课从此不再生效（从课表消失），
> 叠加规则 3 不支持撤销 = 数据损坏路径。现已改为"空即无边界"，并加了倒置区间拒绝（`INVALID_EFFECTIVE_RANGE`）。
> 变异验证：把实现改回丢弃 null ⇒ 3 项往返测试变红（`expected null, but was:<149>` / `<150>`）。
>
> 另两条实现方默认（接线前需与用户确认）：
> - `enabled` / `needsConfirmation` 取**任一为真**（保守）：不因合并让课程静默停用、也不跳过尚待确认的记录；
> - 空白地点按"没有值"处理（真实存储里清空 = **键缺席**，不存在空串值）；同一门课给多条覆盖快照**直接拒绝**
>   （"取哪条"没有合理默认，稳定排序也只是换个样子，结果仍依赖入参）。


## 5. 绝不能动的东西（授权边界）

- `Course.id` 的**语义**：不改成字符串/组合键；已持久化的 id 不得重新分配（合并只允许**减少**记录，不允许重编号）。
- SharedPreferences 键名与 JSON 字段（`course_reminder_settings`、`course_location_overrides` 等）：用户数据契约，只能加不能改；新增字段必须有默认值。
- 提醒键 / `PendingIntent` / 通知标签：合并后必须**先撤销旧安排再按存活 id 重排**，不得留下指向作废 id 的闹钟。
- Room **保持不激活**（阶段 3 最终激活仍另计）。
- 不引入自动合并：**任何**"系统自己决定两条记录是同一门课"的路径都不在本组范围内。

## 6. 第一件可独立交付的东西（**已实现，2026-09-29**）

**纯函数 + 单测**，与组①预览同构，**不接线、不写存储**。已落地于
`app/src/main/java/com/sakata/focusflow/CourseEditPlans.kt`（`internal object CourseEditPlans`），
单测 `app/src/test/java/com/sakata/focusflow/CourseEditPlansTest.kt`（增加不同课次与生效期空档反例）：

1. `CourseEditScope`（单次／该时段后续／整门课程）与其**后果**（只影响单次？会不会新建记录？是否保留原 id？）+ 直接可用的说明文案。
2. `CourseSplitPlan`：输入一条课程与被选中的生效日，输出"原记录改成的样子 + 新记录的样子"（纯数据，不落库）。
3. `CourseMergePlan`：输入多条课程，输出"存活的 id、字段取舍、三个覆盖计数、将被删除的记录数、确认文案"。
4. 三条计划都**可解释**：给出人话理由（沿用组①预览 `NEEDS_REVIEW` + reason 的写法），供确认框直接展示。

这套东西可以在**完全不碰用户数据**的前提下把规则、冲突取舍和边界全测出来；接线与落库留给下一个检查点，并需要用户明确确认。
