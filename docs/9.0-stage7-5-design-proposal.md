### 0.5 本批（纯模型）依据、批准边界与已实现文件

**本批采用 8 条明确规则**（正文中标注"本批规则 N"）：① 课程组独立建模，不复用 `ordinary_items` 成员校验，成员保存完整 `Course`＋课次 id＋父 `courseId`＋原顺序＋通知/地点快照，禁止按同名扩大范围，旧删除无快照不可恢复；② 结构合法与恢复资格分开，结构校验只看版本/字段/ID/成员/期限/快照自洽，用户正常编辑课程不能被历史组阻止保存，动态冲突只在恢复时判断；③ 生命周期独立于当前课程内容，`active/restoring/restored/purging` 均为持久事实，`restored` 是终态且重复恢复返回幂等结果；④ ID 占用与中断恢复分开，`active` 组只要成员 ID 已存在就整组拒绝（即使内容相同），只有持久 `restoring` 才证明核心步骤已启动，`restoring/purging` 不接受新动作也不按普通过期 `active` 处理；⑤ `active` 仅 `now < expiresAt` 可恢复，占用 ID、父课程标题不兼容或有未完成合并/拆分日志则整组拒绝，无关课程变化不影响恢复，允许恢复未确认/停用/已过生效期的数据而由既有调度规则决定是否排提醒；⑥ 不改变提醒开关语义（沿用 `overrides[id] ?: enabled`，不新增"全局关闭一律不排"），`delivered` 只增不减，缺键不视为需要从快照补回，偏好补齐协议留到协调批次；⑦ 清除只处理组恢复负载，不删当前课程、通知覆盖、临时地点或水位，"值等于快照"不算偏好归属证明，已恢复组清除只移除组记录；⑧ 摘要不含自身、字段顺序与格式确定，完整课程列表摘要只作审计，删除请求成员缺失或 scope 不符一律拒绝并要求刷新，快照取提交前真实记录。

**修正批次（相对 `3a05a1d`，三项）**：
1. **严格解码**：新增文件级严格 JSON 助手，拒绝**截断/尾随内容**（`JSONTokener` 解析后必须 EOF）、**类型转换**（版本、所有数值、布尔、字符串都必须是对应 JSON 类型；`"1"`、`"true"`、数字标题一律 Invalid）与**字段缺失**（含 `reminderOverride`/`deliveredAt`/`restoredAt` 必须显式存在，JSON null 是唯一允许的空值写法）。快照与组负载两条解码路径都走同一套助手。
2. **消除地点摘要分隔符歧义**：`payloadFingerprint` 改为长度前缀 + 数量前缀的规范化写法，`a;20001=b` 这样的地点不会再与两条 `a`/`b` 地点产生同一摘要。
3. **父课程字段一致性**：同一 `courseId` 的成员必须在快照内一致地持有 `title` 与 `needsConfirmation`（对应 Room 投影的 `CourseEntity` 父字段与 `CourseRoomProjection` 的"course parent fields disagree"约束）；恢复资格同时校验现存同父课次的两个字段，冲突返回 `ParentConflict(parentId, field, actual)`。

**第二轮修正（相对 `43b8374`，三项）**：
1. **整数无损解码**：所有 Int/Long 字段（根 `version`、`schemaVersion`、`parentIds`、`sourceOrder`、`id`/`courseId`、`deletedAt`/`expiresAt`/`restoredAt`、`deliveredAt` 以及快照内全部数值）统一走"精确整数"路径：只接受 JSON 整数（Int/Long/BigInteger），先做整数性与范围判定**再**转换，绝不 `toInt/toLong` 后补校验。因此 `1.9`、`1.0`、`"1"`、`4294967297`（Int 字段）、`9223372036854775808`（Long 越界）全部 Invalid；`Int.MAX_VALUE`/`Long.MAX_VALUE` 正常接受。
2. **地点日期键规范化**：键必须是该值规范十进制拼写（`key == parsed.toString()`），拒绝 `"020000"`、`"+20000"`、`"2e4"`、`"-0"` 等别名；同一对象内出现两个指向同一天的别名（如 `"20000"` 与 `"020000"`）**整体拒绝**，不再用 `associate` 静默合并（后者会丢弃前一个值）。原始负载不被改写。
3. **父 ID 归属**：对组内快照与"当前课程 + 待恢复课次"的候选合并列表都执行 `CourseRoomProjection.toCourseParentEntities` 的归属约束——父 ID 若同时是课次 ID，该课次必须属于同一父。覆盖两个方向：恢复的父 ID 已被其它课程的课次占用、恢复的课次 ID 已被其它课程用作父 ID；快照内违规 ⇒ 结构 `Invalid`，与现存数据冲突 ⇒ `ParentOwnershipConflict(parentId, conflictingMeetingId, ownership)` 整组拒绝。既有的 `title`/`needsConfirmation` 检查保留；**不**要求同父课次的节次、地点、启用状态一致。

**Legacy 核心存储接入批次（相对 `0b2b276`，A–D 已实现）**：
- **存储契约（A）**：新增键 **`course_recovery_groups_v1`**，与 `courses` 同在 `focusflow` 偏好文件内，因此"课程列表 + 恢复组"可落在**同一次 `Editor.commit()`**。`null`（键不存在）＝合法空集合；空串／损坏／未知版本／结构违规＝`CourseRecoveryGroupsRead.Invalid(reason, raw)`，`raw` 原样保留，**绝不**当空集合、**绝不**自动覆盖。读取与写入都经 `CourseRecoveryCodec`。
- **接口（A/B/C/D）**：`data/CourseRecoveryStore.kt` 定义 `CourseRecoveryGroupsRead`、三个结果类型、`CourseRecoveryStore`、`LegacyCourseRecoveryStore`（真实实现）、`UnsupportedCourseRecoveryStore`（Room 等未接入运行时返回 `NotReady`，**不**静默回退、**不**报成功）；`CoreDataRepository.courseRecoveryStore` 属性按运行时选择。存储原语由 `PrototypeStore` 提供：`withCourseWriteLock`（与 `taskHistoryLock` 同一把锁）、`isStorageReadOnly`、`readCourses`、`loadCourseRecoveryGroups`、`hasPendingCourseEditJournal`、`commitCoursesAndRecoveryGroups`、`commitCourseRecoveryGroups`，`LegacyCoreDataPersistence` 适配器 (`PrototypeStoreCoreDataPersistence`) 同时实现 `CourseRecoveryStorage`。
- **删除同提交（B）**：`deleteCoursesWithRecoveryGroup(expectedCourses, request)` 在**同一把锁内**依次完成：只读保护 → 恢复组可读性 → 未完成合并/拆分日志 → `operationId` 身份去重（重复返回 `AlreadyApplied`，不建第二个组、不二次删除）→ 课程快照比对（失配 `STALE_COURSES`）→ **取提交前真实记录**交给 `captureDeletion`（请求与差集不符即拒绝）→ 课程与 `ACTIVE` 组一次 `commit()`。禁止先 `saveCourses` 再另存组；提交前不更新 UI、不刷新重复任务、不取消闹钟。
- **恢复同提交（C）**：`restoreCourseRecoveryGroup(groupId, expectedGroups, now)` 锁内重读课程与组、**在锁内**探测合并/拆分日志（调用方的旧 pending 标志不作依据），复用 `restoreDecision`；`Eligible` 时按 `sourceOrder` 追加课程（现存课程内容与相对顺序不变）并同时把组写入 `RESTORING`（`transition` 重算摘要），返回 `CoreCommitted`——**核心已提交、后续步骤待完成**；`RESTORING`→`NeedsFollowUp`、`RESTORED`→`AlreadyRestored`（不改数据）、`PURGING`→`NeedsPurgeFollowUp`、占用/父字段/父 ID 归属/过期/陈旧/未完成日志 → 整组拒绝。本批**没有**"标记恢复完成"的入口，也**不**写偏好、不重排提醒。
- **清理与失败（D）**：`purgeCourseRecoveryGroups(expectedGroups, now)` 复用 `purgePlan`，只移除被选中的组记录（过期 `ACTIVE` 与过期 `RESTORED`），**不**动课程、**不**删通知覆盖/送达水位/临时地点、**不**清理仍需续办的 `RESTORING`/`PURGING`，损坏负载永不被清理。提交结果的三种语义在**修正批次**中被明确区分（见下文"提交失败证明修正"）：提交前守卫拒绝 ⇒ `Rejected`；平台确认 `commit()==true` ⇒ `Applied`/`CoreCommitted`；`commit()==false` 或抛异常 ⇒ **一律 `WriteUncertain`**，绝不因普通读回、内存新值或重建对象而报成功；不靠反向覆盖伪装原子事务。
- **业务入口**：`CourseRecoveryOperations`（`readGroups` / `deleteCourses` / `restoreGroup` / `purgeExpired`）为可调用入口；偏好只在捕获时**只读**（`CourseReminders.load` 的覆盖、`CourseLocationOverrides.snapshot`；`delivered_` 因提醒边界暂无读取访问器而按 §2.4 的键格式直读，并有回归测试对账）。
- **仍未接入**：Room 表／迁移（返回 `NotReady`，未占用迁移版本）、偏好补齐与垃圾回收、提醒重排与通知取消、`RESTORED` 完成入口、删除/恢复 UI 与 `MainActivity` 接线；真机未执行。（合并/拆分执行器的统一写锁已在**修正批次**完成，见下。）

## 1. 结论摘要（供快速审定）

1. **课程不是 `Item` 墓碑。** 课次删除是从课程列表里移除记录（`CourseSchedule.kt:41-44`、`MainActivity.kt:1752-1754`），没有 tombstone、没有 `trashSnapshot`。7.3 的组状态机与校验（要求活跃成员在 `items` 里仍是配套 `回收站` 墓碑，`data/TrashJournal.kt:101-103`）**在结构上不适用于课程**，必须另立类型专属状态与校验。
2. **7.3 的组存储当前也装不下课程组。** 组解码硬要求 `group.kind == "ordinary_items"` 且成员快照 `kind ∈ {任务, 收集箱, 暂停}`（`data/TrashJournal.kt:261-267`）。把课程组塞进 `trash_groups_v1` 会立刻被拒。
3. **推荐新增独立存储**：Legacy 新键 `course_recovery_groups_v1`（与 `courses` 同处 `focusflow` 偏好文件，`PrototypeStore.kt:33`，因此核心提交可一次 `commit()` 覆盖课程+组），Room 新表 `course_recovery_groups`（schema v7→v8，同一 `runInTransaction`）。**不**复用、**不**放宽 7.3 已冻结的普通组编解码。
4. **删除本身只需一次核心提交**；闹钟取消与通知撤下是**可从组状态重放的副作用**，不需要额外状态位。**恢复**采用"核心提交（课程+`restoring`）→ 幂等提醒重排（偏好写入推迟）→ 收尾提交（`restored`）"三段，中断可续。**永久清除／到期**只做两步：选择到期的 `active` 组与到期的 `restored` 记录 → **只移除组记录**，不碰课程、通知覆盖、地点或水位。
5. **偏好策略（本批规则 6/7）**：删除、恢复、清除**都不写** `course_reminder_settings`／`course_location_overrides`；组内只保存三态与水位快照；恢复**缺键不补**、不覆盖现值；`delivered_` 只增不减；清除只移除组记录；偏好垃圾回收另行设计。恢复沿用在用的 `overrides[id] ?: enabled`，**不新增**"全局关闭一律不排"的规则。
6. **旧删除不可恢复**：7.5 之前删掉的课程没有任何快照，禁止从 `delivered_*`／`meeting_*` 残留键、历史事件或导入来源反推。
7. `Course` **没有颜色字段**（`CourseSchedule.kt:3-22`），因此"恢复颜色"不存在，不得发明。
8. **跨存储不等于原子**：Legacy 的一次 `commit()` 只覆盖同一偏好文件内的键；`course_reminder_settings`、`course_location_overrides`、AlarmManager、NotificationManager 都是独立存储/系统副作用，必须按幂等协议逐步执行并允许"恢复待完成"。

## 3. 拟议契约

### 3.1 删除集合与完整快照

**【拟议】** 每次用户发起的课程移除，形成一个**课程恢复组**（course recovery group），写入独立的类型专属存储（见 3.3）。组负载（schema v1）：

```
CourseRecoveryGroup {                       // schema v1；本批已实现的纯模型
  schemaVersion: 1                 // 必填；未知版本一律 Invalid，不得当空组
  groupId: String                  // UUID，非空且全表唯一
  kind: "course_closure"           // 固定值（不复用 ordinary_items）
  scope: "meeting" | "parent" | "batch"
                                   // 单行=meeting；同一 courseId 的全部课次=parent；跨父多选=batch
  operationId: String              // 本次操作 ID，用于日志关联与幂等判定
  deletedAt: Long                  // 注入的 now（毫秒）；> 0
  expiresAt: Long                  // == deletedAt + 30×24×60×60×1000；溢出拒绝
  state: "active" | "restoring" | "restored" | "purging"
  parentIds: [Long]                // 成员 courseId 去重后升序；非空且必须与成员一致
  sourceFingerprint: String        // 负载摘要（不含摘要字段自身），固定字段顺序
  restoredAt: Long?                // 仅 restored 终态携带；其余状态必须为 null
  members: [                       // 有序：按删除前列表顺序，sourceOrder 严格递增
    {
      sourceOrder: Int             // 删除前在课程列表中的下标
      id: Long, courseId: Long     // 课次 ID／父课程 ID，必须与 courseJson 一致
      courseJson: String           // 删除前完整 Course 快照（15 个字段全部显式写出）
      reminderOverride: Boolean?   // null＝删除时该键缺席（跟随总开关）；false/true＝显式覆盖
      deliveredAt: Long?           // 送达水位；null＝无该键；> 0
      temporaryLocations: { "<epochDay>": "place" }   // 该课次按日期的临时地点；空＝无
    }
  ]
}
```

**快照必须完整（本批已实现）**：`CourseSnapshotCodec` 写出全部 15 个字段，字段名沿用现有课程编解码（`PrototypeStore.kt:837-849`），可空生效期写显式 JSON null；**不含颜色**（现无此字段）。解码是严格的：字段缺失、取值非法、`id`/`courseId` 与成员不一致都判为不可读，不默认、不补齐。

**三态（本批规则 1/6）**：`reminderOverride` 为 `null` 表示"删除时没有该键"（跟随总开关），`false`/`true` 是显式覆盖；这是三态能原样往返的唯一依据。本批只保存与往返，**不写任何偏好**（见 §3.6）。

**结构校验与恢复资格分开（本批规则 2）**：`structuralError` 只检查版本、kind、id、成员、顺序、期限、**同一父的 `title`/`needsConfirmation` 一致**、快照自洽与摘要一致，**不读取当前课程列表**；因此用户正常编辑课程既不会让历史组变成结构非法，也不会被历史组阻止保存。占用、父字段冲突、到期、未完成合并/拆分日志都属于恢复资格，只在尝试恢复时判定（§3.2、§3.8）。

**负载摘要与请求集合（本批规则 8，已实现）**：`payloadFingerprint` 用固定字段顺序计算 SHA-256，**不包含 `sourceFingerprint` 自身**，且每个变长字段带长度前缀、每个列表/映射带数量前缀（消除分隔符歧义）；`courseListFingerprint` 只用于审计，恢复资格**不要求**整份课程列表未变化。

**整数与日期键的严格性（第二轮修正，已实现）**：所有 Int/Long 字段经"先判整数性与范围、再转换"的精确路径（只认 Int/Long/BigInteger，拒绝 Double/Float/BigDecimal/字符串与越界值）；地点日期键必须是规范十进制（`key == parsed.toString()`），同一对象内的别名碰撞整体拒绝而不是静默合并。解码失败会带出具体原因（`group N is unreadable: …`），避免所有篡改都只报"摘要不符"。`captureDeletion` 以提交前的真实记录建成员，要求"提交后列表 == 提交前列表 − 请求集合"；请求成员在提交前已缺失、scope 不符（`meeting` 恰 1 条、`parent` 必须覆盖该父全部课次且提交后该父不再有课次）、同一次写里还有别的改动、请求为空、id 非法、`now` 溢出、偏好快照损坏、或该课次已属于未收尾组 → **拒绝并要求刷新**，既不缩小也不扩大集合。

**【拟议·范围规则】**
- `meeting`：仅选中课次；同父其它课次保留。
- `parent`（"整门"）：选中集合必须恰为某个 `courseId` 下的全部课次，且提交后该父下不再有课次；不符 → 拒绝并提示刷新。
- `batch`：可跨父；成员仍逐个记录 `courseId`，恢复时不扩张到未选中的同父课次。
- **忽略/清空待确认课**：同样建组，且**原样保留 `needsConfirmation = true` 与 `enabled`**；恢复不会自动确认、不会自动启用（对齐 `Course.confirmImported` 的显式确认原则）。

### 3.2 类型专属状态机与校验（不复用普通 Item 墓碑语义）

**【拟议】** 课程组的活跃/恢复/过期条件与普通组完全不同，必须各自定义：

| 状态 | 判定（纯函数，输入组 + 当前课程列表 + now） | 可用动作 |
| --- | --- | --- |
| `active` | **持久状态**；恢复资格另行判定。成员的 id 只要出现在当前课程列表即为**占用** → 整组拒绝（**即使内容与快照相同**，本批规则 4）；`now >= expiresAt` → 拒绝恢复 | 恢复（未到期且无冲突时）；永久清除；到期后参与清除 |
| `restoring` | **持久状态**：核心恢复步骤已启动、尚未收尾；不按当前课程内容重新推导，也不接受新的手动恢复/清除 | 只走专用续办（`ResumeRestoration`） |
| `restored` | **持久终态**：操作已完成，不要求当前课程永远等于快照；恢复后正常编辑课程不会让它退回 `active`/冲突（本批规则 3） | 幂等结果（`AlreadyRestored`），不改课程、不重复执行业务操作 |
| `purging` | **持久状态**：清除已启动、组记录尚未移除 | 只走续办（`ResumePurge`） |
| 占用 / 父标题冲突 / 已到期 / 合并拆分日志未完成 | **派生判定，不落库**：只在尝试恢复时计算 | 整组拒绝并说明原因；不改变组状态、不进入上述状态 |

**校验（不复用 `verifyActive`）**：
- 课程组成员**不是**墓碑：成员被删后根本不在 `items`/课程列表里；因此**不得**要求"成员仍是配套 `trash_groups` 墓碑"，也不得把 `restoredIds ⊆ members.ids` 那套成员级恢复语义套上来。
- **结构校验（本批已实现，`structuralError`）**：版本与 kind 已知；`groupId`/`operationId` 非空；`deletedAt > 0` 且不溢出、`expiresAt == deletedAt + RETENTION`；成员非空、id 唯一且为正、`sourceOrder` 严格递增；`parentIds` 非空、升序、与成员的 `courseId` 集合一致；每个 `courseJson` 可严格解码且 `id`/`courseId` 与成员一致；**同一 `courseId` 的成员必须一致持有 `title` 与 `needsConfirmation`**（否则无法投影回 Room 的父行）；**父 ID 归属必须满足 `toCourseParentEntities` 的约束**（父 ID 若也是课次 ID，该课次必须属于同一父）；`deliveredAt > 0`、地点键为规范十进制且 ≥ 0、值非空 ≤ 100 字；`restoredAt` 与状态匹配（仅 `restored` 携带）；`sourceFingerprint` 与重算值一致。
- **状态是持久事实，不由当前课程内容推导**（本批规则 3）：只有 `active` 组做占用与父标题检查；`restored` 组对当前课程内容完全免疫。
- **首版只做整组恢复**：不提供部分恢复按钮（对齐交接件 §5.2），失败整笔拒绝，不"恢复其余"。

### 3.4 核心数据同提交

**【拟议】** 只有"课程列表 + 课程恢复组"这一对是**真正原子**的：

| 存储 | 同提交单位 | 边界 |
| --- | --- | --- |
| Legacy | 一次 `SharedPreferences.Editor.commit()`，覆盖 `focusflow` 文件里的 `courses`、`course_setup_done`、`course_recovery_groups_v1` | **仅此一次 commit**；`course_reminder_settings`、`course_location_overrides`、两个日志文件都不在其中 |
| Room | 一次 `database.runInTransaction { … }`，覆盖 `courses`、`course_meeting_rules`、`course_recovery_groups` | 同上；提醒偏好仍在外部偏好文件 |

**【拟议·必须写清的事实】** 删除/恢复**不是**跨存储原子事务：AlarmManager 与 NotificationManager 是系统副作用；两个偏好文件各有自己的 `commit()`。任何"先删课程、随后依次写偏好"的描述都只能说"核心同提交 + 后续幂等步骤"，**不得**称为原子事务。

### 3.5 跨存储执行协议（幂等 + 进程中断恢复）

**【拟议】** 三类操作共用一条串行边界（统一课程写协调锁，见 D10 与 §3.12 第 3 步）与三段式协议。**以下协调与持久化内容本批未实现、也未获本批批准**（本批规则只用于纯模型）。

**（1）删除课程**

| 步骤 | 动作 | 成功后 | 失败后 | 中断后 |
| --- | --- | --- | --- | --- |
| D1 计算与校验 | 由 UI 传入的课次 ID 集合；重读当前课程；按 `captureDeletion` 的真实差集规则校验 scope 与请求一致性；保存成员的通知/地点快照；生成组负载并自检；`now`/`expiresAt` 溢出检查 | 进入 D2 | **REJECTED**：不改任何存储，界面提示需刷新/冲突原因 | — |
| D2 核心提交 | Legacy：`saveCoursesAndRecoveryGroupsIfUnchanged`；Room：`replaceCoursesWithRecoveryGroup`。课程列表去掉目标课次，同时写入 `state=active` 的组 | **APPLIED** | **WRITE_FAILED / STALE_COURSES / INVALID_INPUT**：课程与组都未变（Legacy 未 `commit`、Room 事务回滚） | 同一提交要么全在要么全不在 |
| D3 副作用重放 | 对每个成员 id：`CourseReminders.cancel`（幂等）+ `NotificationManager.cancel("course:$id", 0)`（幂等） | APPLIED 且副作用完成 | 捕获异常并记录；**结果仍为 APPLIED**（列表与组已一致，副作用可重放） | 启动/下一次恢复链按"active 且成员不在当前课程列表"重新执行 D3 |

**（2）恢复课程**

| 步骤 | 动作 | 成功后 | 失败后 | 中断后 |
| --- | --- | --- | --- | --- |
| R1 前置校验 | 重读当前课程；按 `restoreDecision` 判定占用/父标题/到期/未完成日志/续办状态（3.8） | 进入 R2 | **REJECTED**（整组拒绝，含 `restoring`/`purging` 只允许走续办） | — |
| R2 核心提交 | 写回成员课程（按 `sourceOrder` 排序追加）+ 组状态 → `restoring`，**同一次**提交/事务 | 进入 R3 | **WRITE_FAILED / STALE_COURSES / INVALID_INPUT**：课程与组都不变 | 同 D2 |
| R3 提醒重排（偏好补齐**推迟**） | 只按既有规则调用 `CourseReminders.sync`（`overrides[id] ?: enabled`，`nextTrigger` 只排未来）；**本批不写任何偏好**，缺键不补、水位只增不减的写入协议留到协调批次 | 进入 R4 | 捕获失败 → 保留 `restoring`，界面显示"恢复待完成" | 启动恢复链对所有 `restoring` 组重放 R3 |
| R4 收尾提交 | 组状态 → `restored`、写 `restoredAt`（单次 `commit`/事务） | **APPLIED** | **WRITE_FAILED** → 状态仍 `restoring`，下次重放 | 同 R3 |

**（3）到期清扫与永久清除（本批规则 7）**

| 步骤 | 动作 | 成功后 | 失败后 | 中断后 |
| --- | --- | --- | --- | --- |
| P1 选择 | `purgePlan` 只选出到期（`now >= expiresAt`）的 `active` 组与到期的 `restored` 记录；`restoring`/`purging`/不可读记录一律不选 | 进入 P2 | — | — |
| P2 移除组记录 | 只从组存储删除该组记录（单次提交/事务）；课程、通知覆盖、临时地点、`delivered` 水位一律不动 | **APPLIED** | WRITE_FAILED → 记录保留，下次重放 | 重放 |
| — | **偏好垃圾回收**（如未来要做）必须另行设计并证明归属，不能用"值恰好等于快照"当依据；本批不实现 | — | — | — |

**【拟议·三态结果对外统一】** 每个操作对外只返回三种结果之一：
- `APPLIED`（成功，含"副作用已排队/已重放"）；
- `REJECTED` / `WRITE_FAILED`（失败，存储逐字节未变，或整笔回滚）；
- `RECOVERY_PENDING`（已部分推进，需重启/重试收尾）——界面**必须**显式提示"恢复待完成"，并且在收尾完成前**不得**调度半状态提醒（沿用 `CourseReminders.restore` 现有语义：任一日志/组未收尾就放弃本轮课程重排，`CourseReminders.kt:115-117`）。

### 3.6 偏好处理策略：保留至永久清除（推荐）vs 删除时移入组

**【拟议·比较】**

| 维度 | A 保留现值（推荐） | B 删除时移入组 |
| --- | --- | --- |
| 删除时的写入 | 只写核心存储 1 次提交 | 核心提交 + 至少 1 次偏好 `commit()`（两个文件各一次） |
| 失败窗口 | 无跨存储窗口 | 核心已提交而偏好未删 / 偏好已删而组未写，都要额外的未完成态 |
| 用户偏好安全性 | 组记录损坏/丢失也不会丢用户设置 | 组损坏即丢设置（除非另有备份） |
| 恢复动作（本批规则 6） | 只读快照，**不改现值**；缺键不补、补齐协议留协调批次 | 必须重建全部键 |
| 清除动作（本批规则 7） | 只移除组记录，**不动任何偏好键** | 无额外动作 |
| 代价 | 被删课次的键会残留至清除（最多 30 天）；ID 复用时新课程可能继承旧覆盖 | 无残留 |

**推荐 A**，理由：现状本来就不清理这些键（§2.4/2.5 实测），A 不引入新的数据丢失面，把跨存储步骤压到最少，并且天然满足"恢复尊重用户当前设置"（现值永远优先）。B 的残留风险在本仓可控：新课程 id 来自 `newItemId()`（`CourseSchedule.kt:15`），导入与新建都不复用旧 id；且恢复侧有占用判定、清除侧不碰偏好。**ID 复用的主动防护登记为残留**（见 §7）。

**【本批规则 6：偏好写入推迟】** 本批只把三态与水位**保存进组负载并原样往返**，不写任何偏好：
- **缺键不补**：`meeting_<id>` 当前缺席可能表示用户主动取消了覆盖，**不得**据此判定需要从快照写回；
- **水位只增不减**：未来若写入，必须取 `max(当前值, 快照值)`，绝不清零（`markNotified` 单调判定，`CourseReminders.kt:105-111`）；
- **全局开关 `enabled` 永不写入**（删除、恢复、清除都不碰）；
- 地点按**原日期**处理，绝不把旧日期地点挪到其它日期或其它课次（对齐《阶段 6 检查点》"下一周继续使用固定地点"，`docs/9.0-stage6-checkpoint.md:10`）；
- 具体的补齐/保留冲突协议（哪些键该写、写前如何比较）留到协调批次，由那一批单独批准。

### 3.7 提醒、水位与旧广播

**【拟议】**
- **只重建有效未来提醒**：恢复的 R3 直接复用 `CourseReminders.sync`（`CourseReminders.kt:123-143`），其 `CourseReminderPolicy.startAt`/`nextTrigger` 已经排除 `needsConfirmation`、`!enabled`、过期、节次非法、未确认节次表，并只返回未来触发点。恢复**不**为已过去的时间点补发通知。
- **不改变提醒开关语义（本批规则 6）**：恢复沿用在用的 `overrides[id] ?: enabled`（`CourseReminders.kt:21`）——总开关关闭而该课次显式 `true` 时**仍按既有规则处理**；**不新增**"全局关闭一律不排"的规则，也不写全局开关。恢复允许未确认、停用或已过生效期的课程数据，是否建闹钟完全交给现有调度规则（`CourseReminderPolicy.startAt` 已排除这些情形）。
- **送达水位**：本批不写偏好；未来若写入只允许抬升（`max(当前, 快照)`），从不清零。因此（a）删除前已送达的同一 occurrence 不会重弹；（b）恢复后**下一次** occurrence 的 `expectedAt` 大于水位，仍会正常通知。
- **旧广播防重放**：四层现状保护 + 一层补强——① 删除时取消闹钟（D3）；② 投递时 `currentOccurrence` 要求课次存在且触发时刻严格匹配（`ReminderReceiver.kt:58`、`:151-166`）；③ 迟到 > 30 分钟直接丢弃（`:54-57`）；④ 水位单调去重（`:65`）；⑤ **补强**：删除路径新增按 tag 取消已发通知 `NotificationManager.cancel("course:$id", 0)`（现状缺失，见 §2.6）。
- **删除前已到达的广播不能修改新对象**：课程通知只有打开应用与自动消失两种动作（`ReminderReceiver.kt:68-79`），没有"完成/稍后"式动作，故不存在旧动作改写新状态的问题；设计上仍需保证恢复后不把旧 tag 通知重新点亮（D3/P2 都不调用 `notify`）。

### 3.8 冲突与旧数据策略

**【拟议·恢复前置判定】**（逐条给出动作，均 fail-closed）

| 情形 | 判定（本批已实现） | 动作 |
| --- | --- | --- |
| 组已过期（`now >= expiresAt`） | `Expired` | 拒绝恢复；只允许到期清除。边界与 7.3 一致：`now == expiresAt` 即不可恢复、`now == expiresAt - 1` 仍可恢复 |
| **任一**成员 id 现在存在（无论内容是否相同） | `Occupied(meetingId)` | **整组拒绝**，提示"课次 ID 已被占用"；**不得**凭"内容相同"推断用户已恢复（本批规则 4） |
| 快照父 `parentIds` 下现存其它课次的 `title` 或 `needsConfirmation` 与快照不一致 | `ParentConflict(parentId, field, actual)`，`field ∈ {TITLE, NEEDS_CONFIRMATION}` | 整组拒绝，提示需先核对课程归组/确认状态 |
| **候选合并列表违反父 ID 归属**：恢复的父 ID 已被其它课程的课次占用，或恢复的课次 ID 已被其它课程用作父 ID | `ParentOwnershipConflict(parentId, conflictingMeetingId, ownership)`，`ownership ∈ {PARENT_ID_USED_AS_MEETING, MEETING_ID_USED_AS_PARENT, LIVE_LIST_INCONSISTENT}` | 整组拒绝；快照内部违规属结构 `Invalid`（第二轮修正） |
| 删除后**新增**了同父且标题兼容的课次（导入/手动） | 非冲突 | 允许恢复；**不**扩张恢复集合、**不**改动新增课次 |
| 删除后无关课程被编辑/删除/新增 | 非冲突 | 允许；摘要只在删除时自检与审计，**不用**"删除前列表 == 当前列表"这种比较（见下） |
| 全局通知开关被改动 | 非冲突 | 允许；不覆盖现值，不新增"全局关闭一律不排"规则（3.7） |
| 目标偏好键被改动（override/水位/地点） | 非冲突 | 允许；本批不写偏好，只按快照记录（3.6） |
| 课程含未确认／停用／已过生效期 | 非冲突 | 允许恢复数据；是否排提醒由既有调度规则决定（本批规则 5） |
| 有未完成的合并/拆分日志（`pending` 存在） | `PendingCourseEditJournal` | **拒绝**恢复（删除/清除同理由）；沿用 `CourseMergeOperation.kt:77`、`CourseSplitOperation.kt:59` 的 fail-closed 语义 |
| 组本身 `restoring` | `ResumeRestoration` | 只走专用续办；**不**当新恢复，也不按普通过期 `active` 处理（本批规则 4） |
| 组本身 `purging` | `ResumePurge` | 只走续办；`purgePlan` 也不选它 |
| 组本身 `restored` | `AlreadyRestored` | 幂等结果：不改课程、不重复执行业务操作；当前课程是否被编辑过都不影响（本批规则 3） |
| 组负载损坏/版本未知/摘要不符 | `Invalid(reason)` | 拒绝解释与恢复；原始负载保留（3.3）。**purgePlan 也不自动移除不可读记录** |
| 来源字段（学年/学期/候选键）失配 | 不进冲突判定 | 来源字段随 `courseJson` 原样恢复；**不**据此自动归组或覆盖（`docs/9.0-stage6-device-acceptance-handoff.md:59`：来源只是提示） |

**【拟议·快照校验用哪一态】** 恢复资格只用**当前态**判定：成员 id 是否存在（占用即拒绝）、现存同父课次的标题是否兼容。**不得**把"删除前完整列表"与"当前列表"直接比较——删除后新增一条无关课程是正常操作，直接比较会永久拒绝恢复。摘要只在删除时自检与审计（3.1）。

**【拟议·ID 复用】** 恢复时按上表拒绝；同时**登记残留**：不与恢复交互的路径（例如未来"重新添加同一课次"）如果复用了被删 id，会命中旧偏好键。缓解项：恢复时的占用拒绝、清除不碰偏好、新增课程走 `newItemId()`。实现任务中可加一条防御性检查：创建新课次时若 id 命中某非 `restored` 组则重新生成 id（不作为验收阻断项）。

**【拟议·旧数据】**
- 7.5 之前的课程删除**没有快照**：不可恢复，界面**不显示**这些课次的任何"回收站/恢复"入口；禁止用 `delivered_*`／`meeting_*` 残留键、`TASK_*` 历史事件或导入结果反推课程（沿用 `docs/9.0-stage7-1-data-contract.md:24`、`docs/9.0-stage7-3-data-contract.md:48`）。
- 旧课程 JSON 缺 `courseId`：按 `id` 处理（现状），入组时以 `courseId = id` 记录，恢复后仍是旧布局。
- Legacy→Room：新键并入源指纹与导入；Room 组表在 v8 建立；Room 产品激活保持关闭，迁移只在现有激活流程内执行。

### 3.9 到期与永久清除

**【拟议】**
- 保留期与边界沿用 7.3 冻结口径：`RETENTION_MS = 30×24h`，`now >= expiresAt` 到期、`now == expiresAt - 1` 仍有效（`docs/9.0-stage7-3-data-contract.md:29-31`）。
- 清扫时机与 7.3 同类：**机会式**（进入课程恢复界面/应用启动的统一恢复链），不是后台定时器；界面文案必须与实现一致，**不得**承诺"30 天后自动删除"这种会落空的承诺，但**必须**在删除确认与恢复界面写明"保留 30 天，到期清除"（否则等于静默自动删除用户数据）。
- 清除对象边界（**本批规则 7，已实现为 `purgePlan`**）：只选择**组记录**——到期的 `active` 组与到期的 `restored` 终态记录；`restoring`/`purging` 记录与不可读记录一律不选。清除**只移除组记录**，**绝不**删除当前存在的课程（含同 id 的新课程）、通知覆盖、临时地点、`delivered` 水位、`enabled`／`course_period_table`／`course_setup_done` 或其它组的记录。
- **偏好垃圾回收不在本批**：不能用"当前值恰好等于快照"当作归属证明（用户完全可能编辑成相同值，或该键已属于新用途）。若未来要做，必须另行设计并单独批准。
- `restored` 终态记录是否到期清除：**【待审 D6，本批默认：到期后只移除组记录】**。它不影响任何课程或偏好，因此移除是安全的；`restoring`/`purging` 仍必须走各自续办。

### 3.10 UI 契约

**【拟议】**
- **删除确认**（沿用 `PlanCoursesSection.kt:385-396` 的对话框形态）文案补充保留期与可恢复性，例如"课程将从课表移除，可在 30 天内恢复；节次表、提醒设置、地点与历史不会删除"。**不得**写"自动清理已启用"之类与实现不符的话（现状只有机会式清扫）。
- 单条删除、整门（同父全部课次）删除、批量删除分别明确告知将移除**几条**课次，以及其中是否有待确认课程。
- **忽略/清空待确认课**：沿用现有无确认对话框的交互（`PlanCoursesSection.kt:198`、`:130`），但成功后提示"已移入课程恢复，可在 30 天内找回"；若按值相等过滤导致实际移除条数少于请求，提示实际条数（见 §3.1 的差集规则）。
- **建议把多条的"忽略"收敛为一次操作**：现状 `span.records.forEach(onIgnore)`（`PlanCoursesSection.kt:198`）会对 N 条各提交一次（N 个组、N 次乐观校验），任一次失败就出现"部分忽略"；**拟议**改为一次传入整个集合、一次提交、一个组（与批量删除一致）。
- 恢复入口：课程页的独立分区（与"已确认课程"并列），按组展示：删除时间、剩余保留期、成员（标题/星期节次/原 `needsConfirmation`/`enabled`）、整组"恢复"与"永久清除"（二次确认，不可逆）。
- `conflict` 组：显示原因（ID 已被占用/父课程已变），只允许"永久清除"，不允许恢复。
- `restoring`/`purging` 组：显示"恢复待完成/清除待完成，将在下次启动继续"，不显示可点的成功态。
- 无历史快照的旧删除**不显示任何入口**（不做占位、不做"不可恢复"列表）。
- 文案本轮不改版本级更新说明：7.5 不分配版本、不发版（`AGENTS.md:34-35` 只在发版时写 `QuickStartDialog.updateHighlightsFor`）；下次发版必须补课程恢复条目，本轮登记为交接待办。

## 4. 待审决定（每项含推荐与理由）

| # | 决定 | 推荐 | 理由与影响 |
| --- | --- | --- | --- |
| D1 | 课程组存储位置 | **独立存储（Legacy 新键 + Room v8 新表）**，见 3.3-A | 同时满足"核心同提交"与"不放宽 7.3 冻结契约"；代价是新表与迁移 |
