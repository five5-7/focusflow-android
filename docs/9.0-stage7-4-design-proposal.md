#### 2.1.2 `saveItemsWithEvents` 对删除的真实影响

`MainActivity.kt:881` 在写入前会再跑一次 `RepeatActions.refresh(updated, courses = courses)`，把 `generated.items` 与 `events + generated.events` 一起提交。

- **【现状】** 不会为刚删除的模板再生成实例：`refresh` 的模板过滤器在 `RepeatActions.kt:44-45` 要求 `it.kind == "重复模板" && !it.repeatPaused`，而删除后模板 `kind == "回收站"`、`repeatFrequency == ""`，两个条件都不满足。
- **【现状】** 不会把 `stop` 转成「重复历史」的实例复活：它们在 `RepeatActions.kt:61-62` 的 `expired` 过滤里要求 `kind == "任务" && !it.done`，已不满足；`RepeatActions.kt:70-75` 的新实例去重只看 `kind == "任务"` 与 `repeatOccurrenceDay == today`。
- **【现状】** 因此删除当下的净效果是：模板进回收站，原待处理实例变历史并失去时间，提醒被 `syncTaskReminders` 取消。

#### 2.1.3 「受影响的未来实例」当前**没有**显式记录，且项状态不可区分

**【现状】** `stop`（`RepeatActions.kt:130`）选中的集合是 `repeatTemplateId == id && kind == "任务" && !it.done` —— 与 `pause` 的谓词（`RepeatActions.kt:109-110`）**逐字相同**；`cancelInstance` 是单条操作（`RepeatActions.kt:172-179`）。操作后这些实例的 `kind` 都变成 `"重复历史"`，`detail` 取值为 `"本次未处理"` 或 `"规则停止，取消本次"`。同一组取值也被另外两条路径使用：

- `pause`（`RepeatActions.kt:109-116`）：`detail = "本次未处理"` 或 **`"暂停时未处理"`**；
- `cancelInstance`（`RepeatActions.kt:172-179`）：`detail = "本次未处理"` 或 `"本次已取消"`，并额外发 `TASK_DELETED`。

**【现状】项状态是有损的**：

1. `"规则停止，取消本次"` 是唯一由 `stop` 独占的文案，但它只覆盖未被判定为「错过」的那部分实例；命中 `missed` 的实例文案是 `"本次未处理"`，三种操作写入的项状态**完全同形**（`kind="重复历史"`、`detail="本次未处理"`、`scheduledAt=null`、`windowStartAt/EndAt=null`），仅比较项无法归因，也无法判断它是删除、暂停还是取消造成的；
2. 用户在该实例被转为历史**之后**、删除规则**之前**主动跳过的实例带 `REPEAT_SKIPPED`（`RepeatActions.kt:169`），其 `kind` 同样是「重复历史」；
3. `deleteRule` 落盘时只保存了模板自身的 `trashSnapshot`（`RepeatActions.kt:155`），**没有**保存实例 ID 集合；全仓没有 operationId 或批量时间戳之类的字段来标记「属于同一次删除」。

**【现状】事件日志可以部分重建，但不是契约**：非 missed 实例可通过 `TASK_UNSCHEDULED` 的 `extra` 区分——`"停止重复"`（`RepeatActions.kt:144`）／`"暂停重复"`（`:123`）／`"取消重复本次"`（`:184`）；`missed` 实例的 `REPEAT_MISSED` 三处**都没有 extra**（`:141-142`、`:120-121`、`:181-182`），只能靠与同模板 `REPEAT_RULE_CHANGED`(extra `"停止"`，`:139-140`) 的 `recordedAt` 对齐来间接归因。现有最接近的消费者 `RepeatHistorySummary.from`（`RepeatHistorySummary.kt:24-35`）只按 `detail` 字符串分类（`:28-34`），不做时间对齐；**代码里没有任何执行这种重建的函数**。

**【现状】结论**：仅凭持久化的项状态无法可靠回答「上次删除规则影响了哪几个未来实例」；用事件时间戳对齐在统计上**可能**可行，但那是推断，不是代码声明的契约，也不能区分同一时间窗内的暂停与删除。这正是 7.4 必须引入组快照的根因，也解释了 `docs/9.0-stage7-1-data-contract.md:15` 的边界声明「`TrashActions.restore` 可恢复模板，但不能恢复受影响实例；7.4 才提供闭合组恢复」。

#### 2.1.4 重复规则**不会**进入 7.2 的删除组

**【现状】** 三条互相独立的证据：

1. `data/TrashJournal.kt:38`：`private val ordinaryKinds = setOf("任务", "收集箱", "暂停")`；`data/TrashJournal.kt:48` 的删除识别要求 `original.kind in ordinaryKinds`。重复模板的 `kind` 是 `"重复模板"`，`stop` 之后是 `"已停止重复"`，都不在集合内。
2. `data/TrashJournal.kt:142-143`（`TrashJournalCodec.decode` 的 `require`）：解码时把组种类硬编码为 `ordinary_items`，其它种类一律拒绝。
3. 恢复侧 `TrashActions.kt:24-25` 要求 `kind == "回收站"` 且 `trashSnapshot` 非空，与是否成组无关。

**【现状】后果**：重复规则 tombstone **没有** `expiresAt`、不参与 `verifyActive`（`data/TrashJournal.kt:95-106`）一致性校验、也不在 7.3 的到期清理/组恢复界面覆盖范围内。这是 7.3 与 7.4 的接口缺口，见 §7。

#### 2.1.5 重复规则 tombstone 的形状

**【现状】** 以 `deleteRule` 的 `stopped.items` 映射为准（`RepeatActions.kt:152-155`）：

| 字段 | 删除后取值 |
| --- | --- |
| `id` | 不变（原模板 ID） |
| `kind` | `"回收站"` |
| `detail` | `"重复规则已删除"` |
| `trashedAt` | `at` |
| `trashSnapshot` | `ItemsCodec.encode(listOf(template))`，`template` 是**调用前**的原始模板 |
| `repeatFrequency` | `""` |
| `repeatStartDay`／`repeatMinute`／`repeatTemplateId`／`repeatOccurrenceDay` | 落盘项保留原值（`copy` 未清），快照里也保留 |
| `repeatPaused` | `true`（由 `stop` 在 `RepeatActions.kt:133` 设置，`deleteRule` 未清） |

**【现状·语义歧义】** `trashSnapshot` 编码的是**删除前那一刻**的模板。若用户先手动「暂停」规则再删除，快照里的 `repeatPaused == false` 是暂停**之前**的状态吗？不是——`pause` 在 `RepeatActions.kt:113` 已经把 `repeatPaused = true` 写进 live 项，`deleteRule` 的入参 `template` 是 UI 传入的当前项，因此快照会带上 `repeatPaused = true`。反之，若用户先「停止」再删除，快照 `kind` 会是 `"已停止重复"`。**恢复会把 `kind` 整体还原**，因此「先停止、再删除、再恢复」会把一条已停止的规则还原成仍可继续生成的 `"重复模板"`。这是一条需要显式定契约的路径，列入 §8 未决问题 U2。

#### 2.1.6 恢复路径的真实行为

**【现状】** 所有恢复入口最终都是 `TrashActions.restore`（`MainActivity.kt:961`、`1491`、`1538`、`2258-2260`、`2719`）。对重复模板：

- 校验（`TrashActions.kt:24-30`）：`kind == "回收站"`、`trashedAt != null`、`trashSnapshot` 非空，且快照解码后必须 `singleOrNull()`、`it.id == tombstone.id`、`it.trashedAt == null`、`it.kind != "回收站"`。原始模板满足全部条件。
- 恢复后模板回到 `kind == "重复模板"`、`repeatFrequency` 恢复、`repeatPaused` 恢复为快照值。
- `MainActivity.kt:875-892` 随后跑 `refresh`，因此**若恢复动作经过 `saveItemsWithEvents`，未来实例会在同一次提交里被重新生成**，并由 `syncTaskReminders` 重新排闹钟。
- 若某入口直接调用 `restore` 而不经 `saveItemsWithEvents`，则不会立即生成实例；下一个 `refreshRepository` 触点（启动恢复链 `ReminderScheduler.kt:135-138`，或次日 00:05 的 `ACTION_REPEAT_REFRESH`）才会补生成。

**【现状】未恢复的部分**：`stop` 转成「重复历史」的原待处理实例**不会**回到 `kind == "任务"`。恢复后它们仍是历史记录，`scheduledAt` 仍为 null。用户看到的是「规则回来了、今天/未来的实例是新的」，而不是「原来那几个实例回来了」。

**【现状】当天可能不重建新实例**：`refresh` 的两个去重判断都**不看 `kind`** —— `RepeatActions.kt:74-75`（`repeatOccurrenceDay == today`）与 `RepeatActions.kt:84`（候选日冲突）。删除当天被 `stop` 转为「重复历史」的实例**仍保留 `repeatOccurrenceDay`**（`:134-137` 的 `copy` 未清该字段），因此恢复后若当天已有该实例记录，当天不会再生成新实例，要等次日触点。这条会在 R9 覆盖。

#### 2.1.7 【现状·既有缺陷】`class_day` 规则在任何一次 JSON 往返后被静默降级

**【现状】** 这是与 7.4 直接相关的存活性缺陷，必须先记录再设计：

- 编码保留：`ItemsCodec.kt:90` `put("repeatFrequency", item.repeatFrequency)`。
- 解码丢弃：`ItemsCodec.kt:36` `item.optString("repeatFrequency").takeIf { it in setOf("daily", "weekly") }.orEmpty()` —— **`"class_day"` 被归零为 `""`**。
- 生成侧却完整支持：`RepeatActions.kt:26` 接受 `class_day`，`:45` 列入允许集合，`:47-59` 有专门的分支，`:81` 调用 `coursesOn`；UI 也提供该选项（`TodoUi.kt:57` 的 `"class_day" to "有课日"`，`:68` 有专门说明）。

**【现状】后果链**：模板一旦经过一次持久化往返（`replaceTasks` → `ItemsCodec.encode` → 读回 `ItemsCodec.decode`），`repeatFrequency` 变成 `""` → `refresh` 的过滤器（`RepeatActions.kt:44-45`，要求 `repeatFrequency in setOf("daily","weekly","class_day")`）**永不**再为它生成实例。表现为：当天创建时能生成实例，重装/重启后该规则静默死亡。

**【现状】墓碑同样受害**：`deleteRule` 的 `trashSnapshot` 经 encode 写入 `class_day`，但恢复时 `TrashActions.restore` 用 `ItemsCodec.decode` 解出（`TrashActions.kt:27`），`class_day` 被丢弃，**恢复回来的规则同样是死的**。

**【现状】还会伪装**：`TodoUi.kt:215` 的 `when (template.repeatFrequency) { "daily" -> "每天"; "weekly" -> "每周"; else -> "有课日" }` 把 `""` 显示成「有课日」，用户看到的是「有课日规则」而实际是永不生成的空规则。

## 3. 拟议契约：组快照、独立 ID 与关联边

**【拟议】** 以下均为设计，未实现。总原则：**先冻结组快照，再允许恢复**；任何无法从快照证明成员身份的情形一律拒绝，不得把「同名/同规则/同计划」当作同一组。

### 3.1 组种类扩展

**【拟议】** 在 `TrashGroupRecord.kind` 现有 `"ordinary_items"`（`data/TrashJournal.kt:84`）之外新增：

- `"repeat_rule_closure"`：一次重复规则删除产生的闭合组。
- `"plan_binding_closure"`：一次计划删除产生的闭合组。

**【拟议】** 解码校验由「`kind == "ordinary_items"`」（现 `data/TrashJournal.kt:142`）放宽为「`kind in` 已知集合，且该种类的专属字段齐全」。旧记录 `kind == "ordinary_items"` 分支不变，保证向前兼容。

### 3.2 重复规则组契约

**【拟议】** 新增独立于 `Item` 的组负载（不塞进 `Item`，避免污染用户数据契约）：

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `groupId` | 组 ID | 非空、组内唯一，沿用现有 `UUID.randomUUID()` 用法（`data/TrashJournal.kt:84`） |
| `kind` | `"repeat_rule_closure"` | 固定 |
| `templateId` | 模板 `Item.id` | 正数 |
| `deletedAt`／`expiresAt` | 与普通组同一算法 | `expiresAt = deletedAt + 30 × 24h`，`expiresAt > deletedAt`；溢出拒绝（沿用 `data/TrashJournal.kt:79` 的检查） |
| `templateSnapshot` | 删除**前**模板的完整 `Item` JSON | 必须能解出 `singleOrNull()` 且 `id == templateId` |
| `affectedInstances` | **删除动作本身**改动的实例快照数组，每项含 `itemId`、`sourceOrder`、删除前完整 `Item` JSON、`preKind`、`preDetail`、`preScheduledAt`、`preDayOnly`、`preWindowStartAt`、`preWindowEndAt` | 仅收录被本次 `stop` 实际改动的实例（即 `RepeatActions.kt:130` 的谓词命中者） |
| `ruleStateBefore` | `repeatPaused`、`kind` 的删除前值 | 用于区分「删除前规则是运行/暂停/已停止」 |
| `courseContext` | `class_day` 规则所需：删除时的 `coursesOn` 相关课程 ID 与生效区间 | 仅 `repeatFrequency == "class_day"` 时写；用于判定重排边界 |
| `sourceFingerprint` | 模板与每个受影响实例的字段级指纹 | 见 3.4 |

**【拟议·关键区分】** 必须把「删除动作改动过的实例」与「同一模板下的其它历史实例」分开：

- `affectedInstances` **只**收录本次删除改动的实例 ID；
- 已被用户完成（`done == true`）的实例不收录（`stop` 的谓词本就排除 `it.done`，`RepeatActions.kt:130`）；
- 已过期/已转历史的实例不收录（`stop` 只匹配 `kind == "任务"`）；
- 恢复时**只**按 `affectedInstances` 的 ID 精确匹配，**禁止**用「凡 `repeatTemplateId == templateId` 的历史项」或「同名」扩大范围。

**§3.2.1【拟议·状态机不可复用】** 现有组的状态推导建立在「成员 = 回收站墓碑」这一前提上：`state` 由 `restoredIds.size` 推导（`data/TrashJournal.kt:20-24`），恢复识别要求成员 `kind` 由 `"回收站"` 变回 `ordinaryKinds`（`:52-56`），一致性校验要求活跃成员的 `kind == "回收站"` 且 `trashedAt == group.deletedAt`（`:102-103`）。重复规则组**不满足这个前提**：模板是墓碑（`kind == "回收站"`），但受影响实例被 `stop` 改成 `"重复历史"`，**从来不是墓碑**（`RepeatActions.kt:134-137`）。因此新组**不能**复用上述校验与状态推导，必须各自定义：

| 组种类 | 活跃条件 | 恢复条件 | 过期条件 |
| --- | --- | --- | --- |
| `ordinary_items`（现有，**行为保持原样**） | 成员 `kind == "回收站"`、`trashedAt == group.deletedAt`、`trashSnapshot == member.snapshot`（`data/TrashJournal.kt:102-103`） | 成员 `kind` 回到 `ordinaryKinds` 且正文与快照一致（`:52-56`、`:71`） | `now >= expiresAt` |
| `repeat_rule_closure`（新） | 模板 `kind == "回收站"` 且 `trashedAt == deletedAt`；**每个受影响实例** `kind == "重复历史"` 且 `detail` 等于快照的 `preDetail`、`scheduledAt == null`、`trashedAt == null` | 模板回到 `templateSnapshot` 的 `kind`／`repeatFrequency`；受恢复策略（§4.1）支配，实例**不必**回到 `kind == "任务"` | `now >= expiresAt` |
| `plan_binding_closure`（新） | 快照 `planId` **不在**当前 `goals` 中；每个成员的 `goalId == goalIdBefore` 且成员未被单独删除 | 快照 `planId` 重新出现在 `goals` 且指纹一致；成员**不被改写** | `now >= expiresAt` |

**【拟议】** 状态字段不沿用 `restoredIds` 的成员级语义：

- `repeat_rule_closure`：**组状态只有 `ACTIVE` 与 `RESTORED`**（本批已实现为 `RecoveryGroupStatus`）。恢复成功即使有实例被跳过也进入 `RESTORED`；被跳过的实例不进入组状态，而是**逐项**记录为 `restored` / `skipped_past` / `skipped_course`（`RecoveryInstanceStatus`）。失败一律整组拒绝并保持 `ACTIVE`。**不得**沿用 `restoredIds` 的成员级 `state` 推导（U14 已由本批落地关闭）。
- `plan_binding_closure`：**无成员级恢复状态**——恢复只重建 `Goal` 记录，成员一个字段都不变（见 §3.3 与 §4.2），因此需要一个**组级**的「计划是否已恢复」标记，不能靠 `restoredIds`。（现有 `TrashGroupRecord.state` 在 `members` 非空时才可能等于 `"restored"`，见 `data/TrashJournal.kt:20-24`；**空成员的组永远推不出 `"restored"`**，这正是 U8 与本节交叉的技术原因。）

**§3.2.2【拟议·必须按组种类分派的四个位置】** 审查指出「UI 筛选不能证明清理安全」——这一点成立，且我此前正是用 UI 过滤（`TrashView.kt:36`、`:47` 要求 `kind == "回收站"`）去推断安全，推理方式不成立。必须逐个检查底层函数并**按组种类分支**。以下行号指 7.3 提交 `8a3c96b` 的 `app/src/main/java/com/sakata/focusflow/data/TrashJournal.kt`：

### 3.3 计划关联组契约

**【拟议】**

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `groupId`／`kind` | `"plan_binding_closure"` | 同上 |
| `planId` | 被删除计划的 `Goal.id` | 正数 |
| `planSnapshot` | 删除前完整 `Goal` 的 JSON | 必须能解出 `singleOrNull()` 且 `id == planId` |
| `bindingSnapshot` | 成员数组：`itemId`、`sourceOrder`、`goalIdBefore`、成员完整 `Item` JSON、`doneBefore`、`repeatTemplateIdBefore` | **收录删除时所有** `Item.goalId == planId` 的项，**不区分**是否已完成、是否带 `repeatTemplateId` |
| `planRestored` | **组级**「计划是否已恢复」标记 | 布尔或等价状态；成员无状态（见 §3.2.1） |
| `sourceFingerprint` | 计划指纹 + 每个成员的**身份与关联边**指纹 | 见 3.4 |

**【拟议·纳入范围】** 纳入范围只看一条判据：**删除时 `Item.goalId == planId`**。理由与边界：

- **纳入**：所有 `goalId == planId` 的项，包括已 `done` 的、以及带 `repeatTemplateId` 的规则实例。
- **当初排除它们是错的**：本文首版把「已 `done` 的项」与「`repeatTemplateId` 实例」排除在外（原 §3.3 的 U3／U4 待定项），理由分别是「避免双主」与「未定」。但 `onDeleteGoal` **只删 `Goal` 记录，不改任何任务**（§2.2.2），所以这两类任务**仍持有原 `goalId`**；若闭包不记录它们，恢复计划会让它们**静默重新关联**，而组无法证明它们当时属于该计划。**记录范围必须等于真实的关联闭包**，否则 §3.3 的「只恢复计划记录、不改写任务」就失去依据。
- **「双主」担忧不成立**：记录 ≠ 改写。恢复计划组只重建 `Goal` 记录，**不触碰任务的任何字段**（§4.2），因此不存在两个所有者；任务本就一直只有一个 `goalId`。带 `repeatTemplateId` 的实例仍由规则链独立管理其生成与取消，两条链的职责正交。**U3 因此可关闭**（保留为历史记录，见 §8）。
- **不**纳入：`goalId` 为 null、或指向其它计划的项——即使标题相同。
- **【拟议·新增同 ID 绑定】** 删除后新产生的、`goalId == planId` 的项（例如删除窗口内新建任务并挂到同 ID 新计划）：它们**不属于**快照闭包。恢复时若发现存在这类绑定，按 §5.3「计划 ID 已被复用」拒绝，避免把两代绑定混为一谈。**【待定 U15】** 是否改为「允许恢复计划并把这些新绑定一并视为有效」。

**【拟议·U4 关闭】** 已 `done` 的项同样纳入记录（理由见上）；恢复时它们**不需要任何处理**，因为删除与恢复都没有改过它们。U4 保留为历史记录。

### 3.4 源指纹（按组种类分级）

**【拟议】** 指纹强度**按组种类分别定义**，不共用一份「完整内容指纹」——统一用全内容比对会把「不改变归属的普通编辑」误判为冲突（修正见 §5.3）。

| 组种类 | 指纹覆盖 | 用途 |
| --- | --- | --- |
| `ordinary_items`（现有，**不变**） | 沿用现状：成员完整 `Item` JSON 与墓碑快照逐字比对（`data/TrashJournal.kt:50`、`:71`、`:102-103`） | 普通条目恢复必须与快照完全一致 |
| `repeat_rule_closure` | **模板**：`id`、`kind`、`repeatFrequency`、`repeatStartDay`、`repeatMinute`、`repeatPaused`、`title`、`trashedAt`、`trashSnapshot`。**受影响实例：删除后的完整预期状态**（下文 `postState`），不是只挑几个字段 | 恢复**会写入完整 `Item`**，因此必须能与删除后的完整预期状态逐字段核对；核对不通过即冲突 |
| `plan_binding_closure` | 计划：`id` + 完整 `Goal` JSON。成员：**仅** `id` 与 `goalId` 两项 | **只校验身份与关联边**；成员正文（`title`／`detail`／`scheduledAt`／`durationMinutes` 等）**不进**指纹 |

**【拟议·分级理由】** 两条理由不同，不能互相套用：

- **计划组可以只校验 `id` + `goalId`**：计划删除**不改动任何任务**（§2.2.2），且恢复**不改写**任务任何字段（§4.2）。既然恢复不写，就不需要（也不应该）要求正文一致；把正文纳入指纹会让改名、改期这类普通编辑触发整组拒绝。真正需要拦的是**绑定边**变化（改挂、清空、删除）。**该前提一旦不成立（若实现改为回写任务），指纹必须同步升级为全内容。**
- **重复规则组必须核对完整预期状态**：恢复**确实会覆盖完整 `Item`**（见下「恢复语义」）。只挑 `kind`／`detail`／`scheduledAt` 等少数字段不足以保护完整还原——用户在删除窗口内可能给该实例补了备注（`userNote`）、勾了检查项（`checklist`）、改了优先级或时长；若恢复整项覆盖，这些修改会被静默丢弃。因此删除时必须把**删除后**的完整预期状态存进负载，恢复前逐字段核对，不一致即按冲突拒绝。

**【拟议·恢复语义：按字段还原，不做整项覆盖】** 为避免覆盖用户后续修改，重复规则组的恢复**不得**直接用快照整项替换。分两类处理：

| 对象 | 删除动作改了什么 | 恢复应写的字段 | 冲突判定 |
| --- | --- | --- | --- |
| 规则模板 | `kind`→`"回收站"`、`detail`→`"重复规则已删除"`、`repeatFrequency`→`""`；另由 `stop` 置 `repeatPaused=true`、`kind` 路径经 `"已停止重复"` | **只**还原 `kind`、`detail`、`repeatFrequency`（以及 `repeatPaused`，按决策 B1 = 还原删除前值）。模板的其它字段（`title`／`durationMinutes`／`goalId`／`userNote`…）**保持现值** | 现值必须与删除后的完整预期状态一致；否则冲突 |
| 受影响实例 | `kind`→`"重复历史"`、`detail`→`"本次未处理"`/`"规则停止，取消本次"`、清空 `scheduledAt`/`dayOnly`/`windowStartAt`/`windowEndAt` | 按决策 A2：还原为删除前状态（`kind="任务"`、`detail=preDetail`、`scheduledAt=preScheduledAt` 等），**但**若 `done` 等字段在删除后被用户改动，则按冲突拒绝而不是覆盖 | 现值必须等于 `postState`；`postState` 之外的改动一律视为冲突 |

**【拟议·`postState` 的定义】** 每个受影响实例在组负载里存两份状态：`preState`（删除前，用于还原）与 `postState`（删除后、即本次操作留下的状态，用于冲突检测）。`postState` 必须覆盖**完整 `Item`**（含 `userNote`、`checklist`、`priority`、`durationMinutes`、`rescheduleCount` 等），以便区分「还是删除留下的样子」与「用户又动过」。**不得**用「只比对几个字段」代替。

**【拟议】** `TrashGroupRecord` 现有成员已用 `ItemsCodec.encode(listOf(item))` 保存完整原始 JSON（`data/TrashJournal.kt:87`）；指纹与 `postState` 只用于判定失配并阻止写入，而不是解析两遍 JSON 后静默放行。

**【拟议】** 旧数据无指纹时按 §3.5 处理，不得用「无指纹 = 通过」放行。

### 3.5 旧数据与无组兼容

**【拟议】** 明确四类旧数据，各自行为不同：

| 旧数据 | 判定 | 恢复行为 |

### 4.1 重复规则

| 对象 | 删除前 | 删除后（现状） | 组内是否记录 | 拟议恢复动作 |
| --- | --- | --- | --- | --- |
| 模板 `Item` | `kind="重复模板"`，`repeatFrequency` 有值，`repeatPaused` 原值 | `kind="回收站"`，`repeatFrequency=""`，`trashedAt=at`，`trashSnapshot=原模板` | 是（`templateSnapshot` + `ruleStateBefore`） | 用 `templateSnapshot` 替换 tombstone；按 `ruleStateBefore` 决定是否保留用户此后的暂停意图（见 U2） |

**§4.1.0【拟议·「完整还原」的可核对定义】** 恢复不是「用快照整项替换」，而是**按字段还原 + 先核对删除后的完整预期状态**。下表是一个受影响实例的示范；要求是**逐字段**可核对，示范本身不是验收项：

| 字段 | 删除前 `preState` | 删除后 `postState`（存入组负载，用于冲突检测） | 恢复后应为 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | 12345 | 12345 | 12345 | 不换 ID |
| `kind` | `"任务"` | `"重复历史"` | `"任务"` | 还原 |
| `detail` | `"09:00 · 30分钟"` | `"规则停止，取消本次"` | `"09:00 · 30分钟"` | 还原 |
| `scheduledAt` | `T` | `null` | `T` | 还原 |
| `dayOnly` | `false` | `false` | `false` | 删除时被清为 `false`，此处与 `preState` 相同 |
| `windowStartAt` / `windowEndAt` | `null` / `null` | `null` / `null` | `null` / `null` | 同上 |
| `done` | `false` | `false` | `false` | 删除未改；若删除后被改为 `true` → **冲突**，不覆盖 |
| `userNote` | `"先看第三章"` | `"先看第三章"` | `"先看第三章"`（**保留用户删除后写入的新值**） | 删除未改该字段。若删除后用户改成 `"只看结论"`，则现值 ≠ `postState` → **冲突**，**不得**回滚成 `"先看第三章"` |
| `checklist` | `[]` | `[]` | `[]`（**保留用户删除后勾选的项**） | 同上：`checklist`／`priority`／`durationMinutes`／`rescheduleCount` 等一律按此处理 |
| `repeatTemplateId` | 模板 ID | 模板 ID | 模板 ID | 删除未改该字段，故恢复后仍指向模板 |
| `repeatOccurrenceDay` | 该日 | 该日 | 该日 | 删除未清该字段（`RepeatActions.kt:134-137` 的 `copy` 不含它） |
| `trashedAt` / `trashSnapshot` | `null` / `null` | `null` / `null` | `null` / `null` | 受影响实例从来不是墓碑 |

**【拟议·两条判定规则（可直接转成断言）】**

1. **一致性**：恢复后每个字段必须等于「`preState` 中被删除动作改过的字段」+「`postState` 中未被改过的字段」。等价地：**只回滚删除动作本身造成的字段变化**。
2. **冲突**：若某字段的现值既不同于 `postState`（说明被单独改动过）**且**该字段在删除动作中未被改动，则该实例属**被另行修改**——按 A2 的冲突规则处理（拒绝整组，不做部分恢复），**不得**静默覆盖用户的笔记、检查项等。
3. **损坏**：快照或 `postState` 无法解码／ID 不匹配 → 冲突，同样拒绝。
4. **过期与课程不匹配不算冲突**（决策 A2）：这类实例**保留历史、不还原**，且不因此拒绝整组。
5. **幂等**：组一旦恢复（`groupRestored == true`），再次恢复**不得**重复改数据，也不追加事件；返回「已恢复」分类即可。
6. **清理边界**：恢复完成后的组清理**只删除恢复负载**，**绝不能**删除已经恢复的活跃对象（模板或实例）。`ACTIVE` 重复规则组到期时，只允许清除**匹配的模板墓碑**与组负载，实例历史与事件一律保留；计划组到期只删恢复负载，不删成员任务。**不得**为实现这些行为放宽既有 `repeatGenerated` 的通用永久删除保护（`8a3c96b` 的 `data/TrashJournal.kt:183`、`:215-216`）。
7. **按参数判定**：本批的策略实现经参数接收 `now`、`zoneId` 与课程条件，不读系统时间、不依赖 `Context` 或存储（`RepeatClosureRecovery.recover`）。

**【本批已实现】** 上述 1／2／3／4／5／7 已落地为纯策略模块 `app/src/main/java/com/sakata/focusflow/Stage7RepeatClosureRecovery.kt` 及其 24 条单元测试；6（清理）与持久化、UI 接线**不在本批**。

**§4.1.1【拟议·时间与课程策略】** 「受影响实例」的旧 `scheduledAt` 在恢复时可能已过期，`class_day` 规则还依赖课程是否变化。三者必须用**同一套**判定，不能一处按时间、一处按课程各自放行：

| 实例情形 | 判定 | 恢复动作 |
| --- | --- | --- |
| 旧 `scheduledAt` **仍是未来** | `preScheduledAt > now` | 还原为删除前状态（`kind="任务"`、`scheduledAt=preScheduledAt`、`detail=preDetail`），并交给 `syncTaskReminders` 重排提醒 |
| 旧 `scheduledAt` **已过期** | `preScheduledAt <= now` | **不还原为待办**，保持「重复历史」；按下表分流，且**不补发**提醒（对齐 `docs/9.0-stage7-3-dsh-session-handoff.md:18`「只重排有效的未来提醒」） |
| 旧 `preScheduledAt == null`（日期型实例，`repeatMinute < 0`） | 无时刻可比 | 按 `repeatOccurrenceDay` 与「今天」比较，用上一行同一判据 |
| `class_day` 且该日课程**仍命中** | `coursesOn(preOccurrenceDay, 当前课程)` 非空 | 按时间判据处理 |
| `class_day` 且该日课程**不再命中** | `coursesOn(preOccurrenceDay, 当前课程)` 为空 | **不还原**为待办；保持历史，`detail` 记为课程条件不再满足 |

**【拟议·过期与课程不匹配实例的处理】** 保持「重复历史」原样，**本批不新增任何说明性业务事件**：

- 无论删除时 `preDetail` 是 `"本次未处理"` 还是 `"规则停止，取消本次"`，被跳过的实例一律**保持原历史**：不还原为待办、不补发提醒、**不**写入新事件。
- **不得**依据 `detail` 文案反推该实例是否曾被判定 missed；跳过的原因由策略产出 `SKIPPED_PAST` / `SKIPPED_COURSE` 表达，不写回条目。
- 两种情况都**不改** `task_events` 中已有的历史行（事件类型是否用于**恢复动作本身**见 U5，与本条无关）。

**【本批已实现】** 上表的两条跳过路径已落地为 `RecoveryInstanceStatus.SKIPPED_PAST` / `SKIPPED_COURSE`；策略**不产生**任何事件，也不写回条目。

**【拟议·整组一致性】** 上表是**逐实例**判定，但组的恢复是**整组**的：模板与仍有效的实例被恢复，过期或课程不匹配的实例保持在历史态。**组终态只有 `ACTIVE` 与 `RESTORED` 两个**：恢复成功后即使有实例被跳过，组也进入 `RESTORED`；被跳过的实例不出现在组状态里，而是逐项记录为 `restored` / `skipped_past` / `skipped_course`。因此**不存在**「因过期而保留」与「因失败而未恢复」共用 `partial` 的歧义——失败一律是整组拒绝并保持 `ACTIVE`（见 §3.2.1 的状态定义）。**不允许**因为存在过期实例就整组拒绝，也**不允许**把过期实例强行还原成待办。

**【拟议·恢复后的再生成】** 恢复动作本身**不**生成未来实例；未来实例仍由既有 `refresh` 触点生成（`RepeatActions.kt:93-101`，触点为启动恢复链 `ReminderScheduler.kt:135-138` 或次日 00:05 的 `ReminderScheduler.kt:153-157`）。恢复**不得**为保证「恢复即可见」而伪造实例（U7）。

### 4.2 计划及关联任务

| 对象 | 删除前 | 删除后（现状） | 组内是否记录 | 拟议恢复动作 |
| --- | --- | --- | --- | --- |
| `Goal` | 存在 | **被删除** | 是（`planSnapshot`） | 用 `planSnapshot` 重建该行 |

| 关联 `Item` 的 `goalId` | `planId` | 仍是 `planId` | 是（`goalIdBefore`） | 与当前实测值比对；识别改挂／清空冲突，见 §5.3（**不**比对正文） |

| 成员正文（`title`／`scheduledAt` 等） | — | 可被用户合法修改 | 记录在快照中但**不进指纹** | 允许修改，**不**因此拒绝整组（§5.3） |

| 提醒 | 有 | **不变**（任务仍在，提醒无需重排） | 否 | 不动 |

**【拟议·重要推论】** 与重复规则不同，**计划删除本身不修改成员任务**，所以「恢复任务」在多数情况下是空操作；真正需要恢复的是 `Goal` 记录与**绑定关系**。这一点必须在实现中被明确，否则容易写出「把成员整体还原」从而误伤用户在删除窗口内对该任务做出的合法修改。

### 5.3 拒绝与冲突策略

**【拟议】** 计划组恢复前依次校验，任一步失败即整组拒绝。

**【拟议·必须先厘清的基线】** 现状**接受**悬空 `goalId`：`validate(...)`（`data/CoreDataWriteRepository.kt:320-343`）只校验 id 正且唯一、事件 `itemId`／`recordedAt`、活动字段，**不校验 `goalId` 指向的计划存在**；既有测试 `data/CoreDataWriteRepositoryTest.kt:201-211`「unconditional plan replacement matches the legacy save path」在 fixture 的 `Item(3L).goalId = 70L`（`:380`）保持悬空的前提下断言 `APPLIED`。因此下表**不是**对既有行为的复述，而是**为 7.4 恢复动作新加的守卫**；这些守卫只作用于「从计划组恢复」这一条路径，不改变普通写入对悬空 `goalId` 的容忍。

| 情形 | 判定条件 | 策略 |
| --- | --- | --- |
| 计划已不存在 | 快照 `planId` 不在当前 `goals` | **允许**恢复：这正是主用途（计划被删了才需要恢复）。但要求 `planId` 未被新计划占用 |
| `planId` 已被复用 | 当前 `goals` 中存在同 `id` 但计划指纹不同的计划 | **拒绝**，提示 ID 冲突（`Goal.id` 默认取 `System.currentTimeMillis()`，见 `GoalPlanner.kt:6`，理论上可重排，必须校验） |
| **成员正文被普通编辑** | 成员 `title`／`detail`／`scheduledAt`／`durationMinutes`／`windowStartAt`／`windowEndAt`／`done` 等正文变化 | **允许**恢复，**不**拒绝、**不**回写。计划恢复不改任务（§4.2），改名改期与「能否恢复计划」无关。仅记录一条提示（见 U16） |
| 关联改挂其它计划 | 成员当前 `goalId != goalIdBefore` 且 `goalId != null` | **拒绝整组**。理由：改挂是用户在删除窗口内做出的显式归属决定，恢复会静默抹掉它。**这是 U13** |
| 关联被清空 | 成员当前 `goalId == null`（例如被移入回收站，`TrashActions.kt:15`） | **拒绝整组**；绑定边已消失，该成员不再属于此闭包 |
| 成员已进回收站 | 成员当前 `kind == "回收站"` 或 `trashedAt != null` | **拒绝整组**；提示先单独恢复该成员，因为两个 tombstone／两个组会争同一 ID |
| 删除后新产生的同 ID 绑定 | 当前存在 `goalId == planId` 但**不在** `bindingSnapshot` 中的成员 | **拒绝**，提示该计划 ID 已被新绑定占用（见 §3.3 与 U15） |
| 成员已永久清除 | 成员 ID 不在当前 `items` | **拒绝整组**；提示该计划的部分任务已永久删除，无法闭合恢复 |
| 成员被弹性安排改写 | 成员当前 `kind == "任务"` 但 `trashedAt != null`（见 §2.1.8 的 fail-open 路径） | **拒绝整组**；成员状态与快照不符，需人工确认 |

**【拟议·判定顺序】** 上表按顺序求值，先命中者生效：① `planId` 复用 → ② 新同 ID 绑定 → ③ 成员缺失 → ④ 成员入回收站或 `trashedAt != null` → ⑤ 关联被清空 → ⑥ 关联改挂 → ⑦ 全部通过则恢复。正文编辑（第 3 行）**不在**拒绝路径上，只产出提示。

**【拟议】** 重复规则组恢复的对应校验：模板指纹失配（用户此后改过该 tombstone）→ 拒绝整组；`affectedInstances` 中任一实例当前 `kind`／`detail`／`scheduledAt`／`trashedAt` 与快照不符 → 拒绝整组，**不做部分恢复**；`class_day` 规则的时间与课程策略见 §4.1 的「§4.1.1 时间策略」。

### 5.4 未来提醒重排边界

**【现状】** 提醒同步是整表重排：`ReminderScheduler.syncTaskReminders`（`ReminderScheduler.kt:439-443`）先取消 `previous` 全部 id，再按 `updated` 重排；`scheduleTaskReminder` 对 `scheduledAt == null`（`ReminderScheduler.kt:365`）与 `kind in {收集箱, 暂停, 游戏, 活动, 回收站, 重复历史, 重复模板}`（`ReminderScheduler.kt:367`）直接 return。

**【拟议】** 边界：

1. 恢复**只重排未来**：沿用 `TaskReminderPolicy.pendingReminders`（`ReminderScheduler.kt:370`）的既有判定，不补发已过时刻的提醒。
2. 恢复一个重复模板本身**不产生**提醒（`ReminderScheduler.kt:367` 排除 `重复模板`）；提醒来自 `refresh` 重新生成的实例。
3. **恢复与 `refresh` 必须同一次原子写入**：最终接入时，恢复对模板/实例的还原与既有纯 `refresh` 的生成结果必须在**同一次**落盘里形成，**不得**分两次提交（否则会出现「模板已恢复但实例尚未生成」的半状态，中断后无法自愈）。可复用现有路径：Legacy 单次 `commit()`（`PrototypeStore.kt:356-360`／`:380-385`），Room 单次 `runInTransaction`（`CoreDataWriteRepository.kt:286-287`）。**【待定 U7】**：恢复入口是否 **强制**调用 `refresh`；若调用，必须与恢复同写。
4. `dayOnly` 项不排提醒（`ReminderScheduler.kt:367`），与模板 `repeatMinute < 0` 的情形一致（`RepeatActions.kt:96`）。
5. 旧广播不得复活：恢复只经 `syncTaskReminders` 重排，`ReminderReceiver` 的既有新鲜度校验（`ActivityReminderFreshness`／`TaskReminderActionFreshness`）继续生效。
6. **按模板与发生日去重保持不变**：恢复不得绕过 `RepeatActions.refresh` 现有的 `repeatOccurrenceDay` 去重（`RepeatActions.kt:84`；该判断**不看 `kind`**，`RepeatActions.kt:74-75` 同）。
7. 删除前暂停的模板恢复后仍暂停（决策 B1），因此**不生成**实例（`RepeatActions.kt:44` 要求 `!it.repeatPaused`）。

**【本批已实现·纯策略侧】** 上述 1／2／4／7 的判定已落地在 `RepeatClosureRecovery`：`dayOnly` 与定时实例的资格判定、暂停状态还原、以及「有跳过实例仍是终态」。3／6 属接入批次，本批**未**接线。
