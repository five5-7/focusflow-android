# 9.0 阶段 6：首轮课程与提醒检查点

状态：本地候选；未通过本轮 Android 构建、CI 或 OPPO 真机验收；Room 产品激活仍关闭。

## 已落地

1. 课程提醒：课程页提供默认关闭的总开关及按当前课次 ID 的“跟随／提醒／关闭”覆盖。只对已确认、启用、有效日期内且节次合法的课次建立闹钟；按课程节次表在上课前 10 分钟提醒，通知展示当前课程名、实际开始时间和地点。课程、节次表或开关变化后重排；开机、应用更新、时区及时间改变后恢复。接收时回读当前课程，校验课次 ID、日期和计划触发时刻，避免旧闹钟使用过时资料；重复广播在持久层去重，超过 30 分钟的延迟通知丢弃。
2. 本次地点：在已确认课次中修改下一次的临时教室，存储键为课次 ID + 发生日期。提醒发出前回读这一日期的临时地点；下一周继续使用固定地点。允许清除临时地点。若通知已经发出，修改地点不会主动再次弹出通知。
3. 独立提醒：通知加入“10 分钟后提醒”，保留原始设定时间，仅改变下一次通知触发时间；应用内显示原始时间和稍后的下次通知时间。完成和稍后的广播带本轮时间；旧动作不能完成或延后新的轮次。通知操作按钮为完成、稍后，点击通知正文可打开应用。新通知采用独立标签避免与其他提醒的整数 ID 互相覆盖；清除时兼容取消旧版整数 ID 通知。

## 数据与兼容边界

- 原课程仍是一条记录对应一次每周上课。课程设置按现有课次 ID 保存；视觉上的同名合并不是课程身份，故界面写“按课次设置提醒”，不能解释为整门课程覆盖。设置和临时地点放在新增独立偏好文件，不修改旧课程 JSON 和 Room 表结构；原有用户数据无需迁移即可读取。
- 教务网原始行尚未保留学期 + 稳定课程／教学班编号。当前 `syncSchoolCourses` 只按标题、星期和节次等做保守匹配。开始多课次课程模型前，需要同时建立稳定外部身份映射、Room/旧存储迁移、手动合并/拆分的明确归属及导入歧义处理；不得根据同名自动认定同一门课。
- “单次／该时段后续／整门课程”的编辑语义仍需真正的课程主记录和发生实例，再接到界面及恢复性删除。自定义提醒“移入收集箱／开始”的可选动作与跨类型统一调度仍未完成。
- 提醒沿用系统通知权限、精确闹钟可用性和既有系统静音设置；厂商延迟、重启与实际通知表现必须在 OPPO 真机验证。

## 下轮模型迁移顺序

1. 先在教务导入边界确认实际返回行中的课程／教学班稳定字段。`ZjuTimetableClient` 已取得学年和学期并通过 `EXTRA_SEMESTER` 传回，但 `ZjuTimetableParser.parse(payload)` 目前没有接收这些参数，`CourseImportBatch` 也不存外部编号。禁止根据推测字段或同名合并。
2. 建立本地课程主记录 ID 和独立课次规则 ID，把旧 `Course.id` 原样迁移为一课一次的两个 ID；导入时仅在来源、学期、稳定教学班编号均一致且唯一时合并成同一课程。缺号、冲突或同名跨班保留待确认的独立记录；手动合并后须保留原课次 ID 的可追踪映射。
3. 审核 `CourseMeetingRuleEntity.toLegacy(parent)` 当前用父 `id` 还原课次的逻辑：多规则共享父 ID 会造成课次覆盖、提醒设置和手动编辑错位。先让旧存储、Room 投影及影子校验支持一对多，再开启相关产品入口。
4. 之后引入单次实例覆盖（日期＋课次 ID），再实现“单次／此时段后续／整门课程”编辑、手动合并拆分、批量撤回；迁移当前按课次 ID 保存的提醒开关和临时地点。该顺序需含旧数据升级、重复导入、断电恢复与同名不同班测试。
