## 底座结构

`TrashGroup` 与成员用于真实、**新发生**的删除：`groupId`（正且唯一）、`kind`、`deletedAt`、`expiresAt`、`state`、成员的 `itemId`／原顺序／完整原始 `Item` JSON。采用完整快照且保持成员顺序，既有 tombstone 同时保留以兼容旧界面。普通条目恢复后，组状态由 `ACTIVE` 变为 `RESTORED`，不会凭 TaskEvent 反推。`OperationRecord` 仅保留 schema 与写入契约；只有在 7.6 存在完整前后态并可验证之后才写入记录，当前数据库应为空。

- 时间：新组按 `deletedAt + 30 × 24h` 写入过期时刻；到期清理和永久删除暂不激活，留给 7.3。防止溢出并拒绝非正时间。
- 一致性：普通条目 tombstone 与事件、删除组必须同提交。Legacy 通过单一 `SharedPreferences.Editor.commit()` 写 `items`、`task_events`、`trash_groups_v1`；Room 通过同一 `runInTransaction` 写三者。由当前核心仓库单写者执行，旧快照乐观校验失败则整笔不动。存储损坏时拒绝新增删除组和覆盖写，不把损坏数据解释为空组。
- 旧数据：既有 tombstone 在组表缺席时仍由原有 `trashSnapshot` 恢复；迁移不据旧 TaskEvent 填组，不猜测旧删除时间。迁移到 Room 时复制 **当前仍存在** 的新组，保留历史上的孤儿事件。源指纹对旧版无新键的布局保持原算法，存在新键时将其加入指纹。
- 恢复：已存在的新组须核对成员的 tombstone、ID 与原始快照；普通条目恢复后标记完成。仅改变普通 Item，不自动恢复关联目标、活动或重复实例。恢复后的提醒仍由既有 `ReminderScheduler.syncTaskReminders` 只为有效未来任务重新建立。
- 课程：课次 ID 是提醒、通知覆盖和临时地点的键。7.2 不写课程组，不借合并中断日志反推完整旧态。当前 `Course` 没有颜色字段，之后仅恢复实际存储过的颜色。

## 7.2 完成门槛

1. Legacy 原子提交失败、并发 Item 更新、损坏组负载均不新增假的成功组；重启可读同一组和完整成员。
2. Room v5→v6 迁移创建空组表和操作表且保留历史；旧版 v1→v6 链通。新操作在事务失败时全部回滚。
3. Legacy→Room 导入时新组随任务一起进入，无法从旧 `TASK_DELETED` 合成新组；Room 产品激活继续关闭。
4. 普通删除／恢复及批量同次删除按一个 groupId 提交；旧 tombstone 没组仍可恢复；重复规则不通过普通条目组伪装为闭合恢复。

第 7.3 之前，用户界面不展示“30 天自动清理／永久删除已可用”之类承诺。此轮不加可安装产品版本，也不合并、发布。
