## 尚未放行：到期时在途请求可能返回成功

增量中 `ZjuTimetableClient.kt:388-402` 的 `expireSession(id)` 从 `inFlightSessions` 移除条目、设置 `expired=true` 并调用 `transport.cancel()`，**故其选择的语义是到期应中断在途导入**。但 `confirmBlocking` 仍只检查 `pending.canceled.get()`（原提交②的 `ZjuTimetableClient.kt:499-520`，增量新文件约 `:602-623`）；它在 POST 返回后、解析成功前也不检查 `pending.expired`。`restorePendingLocked()` 的 `!isVoid()` 只阻止失败条目回填，**不能阻止已到期的成功结果返回**。

可复现时序：确认请求已进入 POST → 到期回调设置 `expired` 并尝试取消传输 → 传输已收到正文或测试替身不响应取消，仍返回一份合法课表 → 代码只见 `canceled=false`，解析为 Success → `finalizeAttempt(..., restore=false)` 和 `onComplete(Success)`，UI `setResult`／`finish`。真实 `disconnect()` 通常能打断阻塞请求，但不能成为阻止这条时序的唯一判据。类似地，到期发生在确认线程启动、POST 尚未执行时，代码也未据 `expired` 阻止启动请求。

修正范围：客户端在准备发送、POST 返回及成功收尾的路径均应识别条目已到期；**最后的成功／失效决策须和到期移除在同一锁下定序**，避免“检查未过期→到期→仍投递成功”的窗口。到期造成的失败应带 `sessionInvalid=true`，让 ViewModel 清旧选项；文案可写“本次登录已过期，请重新登录”，无需把到期误写成用户取消。不要依赖传输替身一定抛异常，也不要让失败路径把条目回填。

可证伪测试：

1. 使用会**忽略 cancel** 的可控假传输，让 POST 到达后阻塞；触发 `RecordingExpiryScheduler.fireAll()`，再释放一份合法课表。结果必须是 `Failure(sessionInvalid=true)`、没有 `Success`，原句柄不能再次请求。
2. 让确认线程在 POST 之前暂停，触发到期再放行；断言没有发出课表 POST，结果仍为无效会话。现有“到期时在途确认”测试给 POST 配的是**没有排队响应**的假传输，解除阻塞后本来也会抛错，故无法检测“合法响应照常成功”这条缺陷。
