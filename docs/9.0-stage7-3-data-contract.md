# 9.0 阶段 7.3 · 删除确认、到期清理与永久清除数据契约

状态：2026-09-30 审定稿，先于任何永久删除代码。分支 `stage7/7-3`，基线 `4b3cf7d`（含 `d5576ab`）。范围仅普通任务／收集箱（`kind ∈ {任务, 收集箱, 暂停}`）；重复规则属 7.4、计划属 7.4、课程属 7.5，本文不改其删除契约。Room 产品激活保持关闭。

本文是 7.3 的实现与复核依据。凡本文冻结的边界，实现与测试必须一致；偏离即阻断缺陷。

## 1. 现状与缺口

`TrashGroupRecord`（`data/TrashJournal.kt:12`）由 7.1/7.2 落地：`groupId`、`deletedAt`、`expiresAt`、有序 `members`（`itemId`／`sourceOrder`／完整 `snapshot`）、`restoredIds`，`state` 派生为 `active`／`partial`／`restored`。写入经 `TrashJournal.update`（同文件 `:41`）与 `verifyActive`（`:95`）校验，Legacy 单次 `SharedPreferences.commit()`（`PrototypeStore.kt:347`）、Room 单次 `runInTransaction`（`CoreDataWriteRepository.kt:154`）。

7.3 开工前的三个真实缺口（均已静态核对）：

1. **永久清除在数据层不可能**。`update` 的 `verifyActive`（`TrashJournal.kt:101-103`）要求每个未恢复成员在 `items` 里仍是配套 tombstone；把 tombstone 从列表移走会 `require` 失败 → Legacy 写返回 `false`（`PrototypeStore.kt:350-354`）、Room 退化为 `invalidInput`（`CoreDataWriteRepository.kt:160-161`）。因此不能只过滤列表。
2. **`expiresAt` 从未与任何 `now` 比较**。全仓无回收站过期清理函数；`expiresAt` 只被写入、持久化、回读校验（`TrashJournal.kt:79/85/114/138/143`）。
3. **单条删除路径缺确认**。批量路径已确认（`TodoUi.kt:192`、`TodayScreen.kt:558`），三条单条路径没有：`onAbandon`（`MainActivity.kt:1531`）、日程时间轴删除（`:1594`）、待办详情删除（`:2713`）。

`TrashDialog`（`TrashDialog.kt`，28 行）是扁平列表：只逐条恢复，不显示分组、剩余保留期，也没有永久清除。

## 2. 删除确认契约

- 每个用户主动发起的「移入回收站」都必须先确认；`TrashActions.trash` 是纯函数，确认只存在于 UI 层，数据层不感知。
- 已确认的批量路径（待办批量、收集箱批量）不改。
- 新增确认覆盖三条单条路径，收敛为一个共用确认（同屏 `mutableStateOf` + `AlertDialog`，与 `TodoUi.kt:192-204` 同型）；`confirmButton` 用破坏性动词「删除」，`dismissButton` 用「取消」。
- 确认文案必须说清去向与可恢复性，不得承诺未实现的自动清理（见 §7）。
- 关联下一步子任务的记录仍按既有语义拒绝删除并提示（`TrashActions.trash` 的 `parentCaptureId` 前置条件，`TrashActions.kt:11`）。

## 3. 保留期与到期边界

- 保留期常量 `RETENTION_MS = 30 × 24 × 60 × 60 × 1000 ms`（`TrashJournal.kt:37`）。**30 × 24 小时是绝对时长，不是「30 个自然日」**；时区、夏令时、跨月都不参与计算，比较用 epoch 毫秒。新组写入 `expiresAt = deletedAt + RETENTION_MS`，并保留既有溢出守护 `deletedAt ≤ Long.MAX_VALUE - RETENTION_MS`（`:79`）。
- **边界冻结：`now >= expiresAt` 即到期**。故 `now == expiresAt` → 可清理；`now == expiresAt - 1` → 必须保留且可恢复。语义是「保留满 30×24 小时」。
  - 本仓存在相反先例 `ZjuTimetableClient.kt:545`（严格大于）。本阶段**不**沿用该先例：此处 `expiresAt` 是绝对时刻戳，`>=` 与其命名一致。两套惯例只差 1 毫秒，因此必须由测试显式钉死，不允许由实现顺手决定。
- 判定输入为 `now`，与 `TrashActions` 既有 `at: Long = System.currentTimeMillis()` 惯例一致；生产调用点由 UI 注入当前墙钟，测试显式传值。不引入 `Clock` 抽象（与全仓惯例一致）。

## 4. 可清除对象（清理对象边界）

「可清除」= 可以永久移除的 tombstone。判定为纯函数，输入当前 `items`、`groups`、`now`：

| 对象 | 可被到期清理 | 可被用户手动清除 |
| --- | --- | --- |
| 组的**未恢复**成员（`itemId !in restoredIds`），且 `items` 中仍是配套 tombstone | 是，且 `now >= expiresAt` | 是（无需到期） |
| 组的**已恢复**成员（`itemId in restoredIds`） | **否** | **否** |
| 无组的 tombstone（7 之前遗留；快照可读，含已删除的重复规则模板） | **否** | 是 |
| 活跃条目（非 tombstone） | 否 | 否 |

三条硬规则：

1. **已恢复成员绝不能被清除。** 恢复后 `items` 里是活跃条目而非 tombstone；按 id 删 `items` 会删掉用户正在用的数据，且 `verifyActive` 跳过已恢复 id（`:99`）不会拦住。因此清除前必须逐成员比对「`items[id]` 仍是 kind=="回收站" 且 `trashedAt == group.deletedAt` 且 `trashSnapshot == member.snapshot`」，与 `:102-103` 同一谓词。
2. **无组 tombstone 绝不自动清理。** 旧数据没有可信 `deletedAt`，禁止凭缺失组或旧 `TASK_DELETED` 推算到期（`docs/9.0-stage7-1-data-contract.md:24`）。它们仍逐条可恢复，只是需要用户显式清除。
3. **重复规则产生的 tombstone 不参与清除。** `TrashActions.trash` 保留 `repeatTemplateId`／`repeatOccurrenceDay`，而 `RepeatActions.refresh`（`RepeatActions.kt:83-86`）只要「当前没有任何条目带该模板 id 与该 occurrenceDay」就会**重新生成**该日实例。清除 tombstone 会让被删的重复实例在下次刷新复活。重复规则的删除契约属 7.4，故 7.3 将快照含 `repeatTemplateId != null` 的 tombstone 排除在清除之外，并在界面说明；此边界登记为残留，交 7.4 收口。
   - 本规则**不含**「已删除的重复规则模板」：`RepeatActions.deleteRule` 写出的 tombstone 快照 kind 是 `重复模板`、且不带 `repeatTemplateId`；`refresh` 只从**活着的** `重复模板` 生成实例，删掉的模板不再是生成源。因此它是无组 tombstone，按上表第 3 行可手动清除，也绝不被自动清扫。
4. **「已恢复」按组判定，禁止跨组取并集。** 同一 id 可以先被删除（G1）、被恢复（G1 变 `restored`）、再被删除（G2）：`update` 的重复组守卫只拒绝 `state != "restored"` 的组（`:80-82`），所以 G1（历史）与 G2（活跃）会并存。此时判定与移除都只针对**把该 id 当活跃成员持有的那个组**；若用全 journal 的 `restoredIds` 并集去拒绝，界面会显示可清除而数据层永远拒绝，并使整轮到期清扫因单条失败而整体停摆。
   - 对同一 id 的清除**不会**改动持有它为已恢复成员的组：`members`／`restoredIds` 都原样保留，`restoredIds ⊆ members.ids` 仍成立，日志依然可读。
   - **到期判定同样按组。** `expiredIds` 只从**把该 id 当活跃成员**的组里取成员。历史 `restored` 组仍可能列出同一 id，但它的旧 `expiresAt` **不得**用来清除后来重新删除的条目——否则保留期被压缩（最坏约提前 30 天；若用户在历史组过期后才恢复并重新删除，下次打开回收站就在几秒内清掉），而界面同一时刻仍显示「剩余 30 天」。

## 5. 清除效果与状态机

清除 `id` 的效果，全部在同一次提交内完成：

1. 从 `items` 移除该 tombstone。
2. 从所属组的 `members` 移除该成员，**并同时**从 `restoredIds` 移除该 id。
   - 不可只删 `members` 而留下 `restoredIds`：`encode`（`:111-123`）不校验而 `decode`（`:145`）要求 `restoredIds ⊆ members.ids`，会写出自己读不回来的负载，下次启动即砖。
3. 若某组 `members` 因此为空，**整条组记录删除**。`decode` 要求 `members.isNotEmpty()`（`:143`），不能留空组。
4. **不新增 `state` 取值。** 组状态仍只有 `active`／`partial`／`restored`；被清空的组直接消失，不引入「已清除」态。
5. **`task_events` 一律不动。** 清除只删条目，不删历史：`TASK_DELETED`／`TASK_RESTORED` 事件保留为审计记录（与 `LegacyMigration`／`TaskHistory` 既有的「孤儿删除事件只作历史保留、绝不据此重建条目」一致）。`appendTaskEvent`／`replaceTaskEvents` 是独立的用户历史功能，与本操作无关。
6. 不动其它组、计划、课程、重复规则、偏好。

## 6. 失败、回滚与幂等

- **原子性**：清除与 `items` 写入必须在同一 `commit()`（Legacy）／同一 `runInTransaction`（Room）内。校验抛 `IllegalArgumentException` 时：Legacy `catch` → 返回 `false` 且**一个键都不写**（`Editor` 未 `commit`，无部分写入）；Room 在事务内即被捕获 → 返回 `INVALID_INPUT` 且事务内未落任何键（`WRITE_FAILED` 只留给存储层自身抛异常的情形）。禁止部分清除。
- **任一成员谓词不符即整体中止**，不得跳过继续清其余成员。
- **幂等**：`purgedIds` 中在 `before` 里已不存在的 id 视为无需处理（no-op），不是错误。因此重复点击、重启后重试、到期清扫与手动清除交错都不会报错，也不会二次破坏。
- **损坏组**：`trash_groups_v1` 解码失败必须继续 fail-closed（拒绝新增组与覆盖写，`Stage7TrashPersistenceTest.kt:44-59` 已钉死），**绝不把损坏数据当空集合继续写**。运行时隔离/备份不在 7.3 范围，登记为残留（见 §9）。
- **乐观快照失配**：清除在锁内／事务内重读当前状态后再判定，不把调用方快照当权威；清除 API 不接受调用方快照，因此**不会**返回 `STALE_TASKS`（该状态属既有的 `replaceTasks*` 路径）。调用方快照过期时整笔不动：Legacy 返回 `WRITE_FAILED`，Room 返回 `INVALID_INPUT`。两者都满足 `.applied == false`，UI 只依赖该标志。
- **写入故障**：Legacy `commit()` 返回 false → 返回 false，内存快照由调用方重读；Room 异常 → 回滚 + `WRITE_FAILED`。

## 7. 竞态、时钟与重启

- **恢复 vs 清理竞态**：两者走同一锁／同一事务。先到者生效，后到者因成员已非「配套 tombstone」而整体失败（fail-closed），绝不部分应用、绝不把已恢复的活跃条目当成待清 tombstone。
- **时钟回拨**：判定只读 `now` 与已存 `expiresAt`；回拨只是少清理，不会回写、不会复活已清除数据。清除不可逆，这是设计而非缺陷。不清除任何「因回拨而未到期」的对象。
- **重启**：组与 tombstone 同一次提交落盘，进程死亡不丢恢复能力（`TrashActions.kt:5`）。重启后到期判定等价于同参数重算，无额外状态。
- **通知**：清除走与删除同一收口 `saveItemsWithEvents` → `ReminderScheduler.syncTaskReminders`（`MainActivity.kt:888`），对 `previous` 逐 id 取消闹钟。清除后条目 id 不存在，`restoreTaskReminders` 不会重建；已投递广播由 `ReminderReceiver` 的 id 复查与 `TaskReminderActionFreshness`（拒绝 `回收站`／`scheduledAt == null`）挡住。**唯一补充**：闹钟取消不等于通知卡片消失，清除后需显式 `NotificationManager.cancel(((taskId + 40_000L) % Int.MAX_VALUE).toInt())`（id 公式见 `ReminderReceiver.kt:606`）。
- **恢复只重排有效的未来提醒**，旧广播不能复活（`ReminderScheduler`：`scheduleTaskReminder` 跳过 `回收站` 等 kind，`TaskReminderPolicy` 只产出未来触发点）。

## 8. 界面契约

- 回收站视图按组渲染：组标题含成员数与**剩余保留期**（由 `expiresAt` 计算，只陈述已实现事实），成员行含标题、原 kind、删除时间；提供条目级恢复、**整组恢复**、条目级与组级**永久清除**（清除前二次确认，不可逆）。
- **无组 tombstone 必须有兜底分区**，否则重复规则模板与 7 之前遗留记录会从列表消失（相对现状的可见性回退）。该分区只提供恢复与手动清除，不显示保留期。
- 状态展示：`partial` 组需显示「部分已恢复」。
- **不得承诺未实现的自动清理。** 本阶段的到期清理是打开回收站视图时的机会式清扫，不是后台定时器。文案必须与实现一致（例如说明保留 30 天、到期后在打开该页时清理），禁止出现「30 天后自动删除」这类会落空的承诺。
- 既有确认文案（`TodoUi.kt:195`、`TodayScreen.kt:561`）随实现更新。版本级「更新说明」（`QuickStartDialog.updateHighlightsFor`）**本阶段不改**：7.3 不分配版本、不发版，按 `AGENTS.md` 只在实际发版时写该版本变化；下次发版必须补回收站相关条目，本轮登记为交接待办。
- 清除后通知卡片按 §7 取消。

## 10. 测试门槛（实现后必须执行）

针对以下输入补必要测试，边界由测试钉死：

1. 单删／批删 → 重启 → 部分恢复／全部恢复（既有 + 组级恢复）。
2. `now == expiresAt - 1` 保留且可恢复；`now == expiresAt` 清除；`now == expiresAt + 1` 幂等 no-op。
3. 旧 tombstone（无组）：可恢复、绝不被自动清理、可手动清除。
4. 损坏组负载：拒绝写入且不替换旧数据。
5. 写入故障回滚：清除失败时 items 与 groups 逐字节不变。
6. 重复永久清除：第二次为 no-op。
7. 恢复与清理竞态：后到者 fail-closed，不部分应用。
8. 已恢复成员不被清除（其活跃条目必须原样保留）。
9. 清除后 `task_events` 保留，组记录按 §5 规则 3 消失或收缩。
10. 清除负载经 `TrashJournalCodec` 往返可读（`restoredIds ⊆ members.ids`）。
