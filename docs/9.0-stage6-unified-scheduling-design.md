## 1. 本件回答什么、不回答什么

**回答**：现状到底碎在哪（逐类型矩阵）、哪些是**真缺口**哪些只是**命名/结构隐患**、以及第一件可独立交付的东西。

**不回答**：不改任何通知行为。本件是设计与授权边界件，任何涉及"哪一类提醒在什么时候被重排"的改动都需要单独确认。

## 2. 现状矩阵（逐项读代码得出，不是推断）

| 类型 | 调度入口 | 恢复路径 | 策略来源 |
|---|---|---|---|
| 课程 | `CourseReminders.sync` | `RestoreAll` → `CourseReminders.restore`（`ReminderScheduler.kt:68`） | `CourseReminderPolicy` + `CourseReminderSettings` |
| 活动 | `ReminderScheduler.scheduleActivityReminders` / `scheduleActivityEnd` | `RestoreAll` → 内联（`:39-60`） | `ScheduledActivityPolicy` |
| 任务 | `ReminderScheduler.scheduleTaskReminder` | `RestoreAll` → `restoreTaskReminders`（`:66`）；**另有** `SettingsScreen.kt:752/771` 只恢复任务 | `TaskReminderPolicy` |
| 独立提醒 | `StandaloneReminders` | `RestoreAll` → `restoreStandaloneReminders`（`:67`） | 自带 |
| 每日状态签到／饭点／收尾 | `:61-63` | `RestoreAll` → 同处 | `PrototypeStore` 设置 |
| 重复刷新／漏做摘要 | `scheduleRepeatRefresh` / `scheduleMissedDigest` | `RestoreAll` → `:38`、`:65` | `RepeatActions` |

`RestoreAll` 指统一恢复入口（**2026-09-29 已改名为 `ReminderScheduler.restoreUnifiedReminders`**，原名 `restoreActivityReminders`；见 §4 第二步）。

所以"两份清单"描述的是**枚举里的类型**，不是"全部提醒入口"。

## 3. 四条结论（一条真隐患、一条已澄清、两条需后续动作）

1. **命名撒谎（结构性隐患，已修）**：统一入口原名 `restoreActivityReminders`（**基线**位置 `ReminderScheduler.kt:36-69`；
   改名后声明在 `:98`），
   **于 2026-09-29 改名为 `restoreUnifiedReminders`**（见 §4 第二步）。改名前的状态是：实际恢复 **9 类**
   （按分组 6 组：活动、每日三项、重复刷新／漏做摘要、任务、独立提醒、课程），名字却只说"活动"，
   于是任何**新的恢复入口**只要照着名字调它，就会**静默漏掉游戏提醒**——漏掉不会报错，只会在"该响的时候没响"。
2. **游戏提醒只在一个调用点被恢复**：`BootReceiver.kt:25`。与第 1 条叠加 ⇒ "恢复入口覆盖每一类提醒"这件事
   **只靠人记得**，没有任何东西守着。
3. **已澄清（不是缺口）**：曾怀疑"课程提醒不在恢复路径里"，逐行核对后确认 `ReminderScheduler.kt:68` 确有
   `CourseReminders.restore`。**结论修正为命名问题，不是覆盖缺失。**（这一条留在文档里，避免下一个人重复怀疑。）
4. **可达性有限的缺陷（本组范围内，需单独确认后才修）**：统一入口里有一句早退 ——
   `val repository = (runtime as? CoreDataRuntimeResolution.Ready)?.repository ?: return`。
   当核心数据运行时落到 `Blocked` 时，函数会**在活动这一步直接返回**，
   跳过每日三项、重复刷新、**任务**、**独立提醒**、**课程**——一句错也不报，只是提醒不再补上。
   **可达性如实说**：`Blocked` 在代码里有生产路径（`CoreDataRuntime.kt:44` catch、`:47` source==NONE、
   `:55-57` 仓库装配失败、`:59` source 不一致、`:63-68` 任务历史迁移失败），但触发条件是**异常或损坏分支**；
   出厂配置下需要 marker 处于 Failed/Invalid/Activating/Active（激活流程硬编码关闭）或迁移抛异常，
   **本构建未取证真机可达**（测试里能构造，但那不是出厂配置）。放大因素：`resolve` 结果按**进程缓存**
   （`CoreDataRuntime.kt:33-38`），一旦某次落到 `Blocked`，本进程后续所有恢复都会继续早退。
   修复＝把早退收窄到只管活动那一步；**注意任务与课程各自也有同样的 `Blocked` 早退**
   （`restoreTaskReminders`、`CourseReminders.restore`），所以只收窄这一处**并不能**让它们恢复——
   真正会因此恢复的是每日三项、重复刷新里的闹钟部分、以及独立提醒。这属**行为变更**，需单独确认与真机验收。
   **本步只登记、未修**，以保持"结构改动与行为改动分开"（AGENTS.md）。

## 4. 第一件可独立交付的东西（**已实现，2026-09-29**）

- 统一入口改为按 `REMINDER_RESTORE_ORDER` **遍历**（各步内容逐条照抄，含原有的早退语义，故**零行为变化**）；

### 4.1 这套数据**不能**保证什么（复核席 B 逐条盘出，照登）

1. **不检查每一步做了什么**：把 `COURSE -> CourseReminders.restore(context)` 改成 `-> Unit` 或调错函数，
   4 条测试仍全绿——列表只决定"跑哪些、什么顺序"，分支体是手写的。
2. **`else -> Unit` 是逃生门**：一旦有人加 `else`，编译器不再强制穷尽，此时"加常量 + 登记 + 同步改顺序断言"
   可以三条全绿而该类型**永不恢复**；而编译报错时最省事的修法恰恰是加 `else`。
3. **顺序断言的语义有限**：它把当前顺序钉成"字面量 vs 常量"，不含"为什么是这个顺序"；改两处即全绿。
4. **枚举是手工清单，不是全量提醒口径**：在用通知渠道有 **10 个**（`ReminderReceiver.kt:1050-1059`，
   另有 `QuickCaptureService.kt:76` 一个、以及 3 个升级时清理的废弃渠道 `:1061-1062`），另有若干测试/一次性的调度函数；
   **新增"渠道 + ACTION + 调度函数"而完全不碰枚举 ⇒ 没有任何守卫**（守卫只在有人往枚举加常量时才生效）。
5. **矩阵不等于全景**：`SettingsScreen.kt:752/771`（只恢复任务）与 `ReminderReceiver.kt:55/60`（只恢复课程）
   不在两份清单内。
6. **不保证"真的排上了闹钟"**：各步内部可能因设置关闭而 no-op——那属提醒策略，不属本守卫。
7. **不保证统一入口还有调用点**：删掉 `BootReceiver.kt:24` 与 `MainActivity.kt:1072` 的
   `restoreUnifiedReminders` 调用，四条测试**全绿**（源文本守卫只钉 `restoreGameReminders(`）。
   也就是说"清单齐全"与"入口真的被调用"是两件事。

**第二步（**已完成，2026-09-29**，纯结构提交、零行为变化）**：把统一入口改名为
**`restoreUnifiedReminders`**，调用点 2 处（`BootReceiver.kt:24`、`MainActivity.kt:1072`）+ KDoc 1 处。

> 名字没有采用本件早先提的 `restoreAllReminders` / `restoreEveryReminderType`：**"All/Every" 会把游戏提醒也含进来，
> 而它并不在这个入口里**（那正是第三步要做的行为变更）。`restoreUnifiedReminders` 与
> `REMINDER_RESTORE_ORDER`（统一入口负责的 9 类）口径一致，不再对覆盖面作出超过实际的承诺。
> 改名只动符号：全仓无字符串/日志引用旧名（已核），故行为不可能改变；三个文件的 CRLF/混合行尾用**字节级替换**保住，
> diff 恰为 4 行（1 声明 + 2 调用 + 1 注释）。

**第三步（**行为变化**，需单独确认，不在本件授权内）**：把游戏提醒并入同一个恢复列表，
使任何调用点都自动覆盖它。这会改变"何时恢复游戏提醒"，必须有真机验收。

### 4.2 第三步动手前必须知道的两件事（复核席实测，2026-09-29）

1. **`git add` 会把 `ReminderScheduler.kt` 整文件行尾归一**：该文件在 HEAD/index 里是**混合行尾**
   （412 CRLF + 297 LF），而本机 `core.autocrlf=true`（系统级配置）且仓库**无 `.gitattributes`** ⇒
   普通 `git add` 写入的 blob 会变成"去掉全部 CR"的版本，diff 从 4 行膨胀成约 412 行换行改写。
   本次改名是靠**字节级替换 + 字节级暂存**（绕过 clean 过滤器）做到的。**第三步务必沿用同样方式**，
   否则一个符号改名会淹没在行尾噪声里。
2. **构建产物仍是旧名**：`app/build/intermediates/**` 里的 dex（2026-09-28 生成）仍含 `restoreActivityReminders`，
   因为改名后没有重新 `assembleDebug`。`app/build/` 被 `.gitignore` 忽略、不影响提交与单测证据，
   但**没有任何 APK 反映这次改名** ⇒ 真机验收前必须重新构建。

## 5. 绝不能动的东西（授权边界）

- 通知渠道 ID（`focusflow_course_reminders_v1`、`focusflow_quick_capture_v1` 等）、通知标签、`PendingIntent` 身份：用户可见契约。
- 通知行为保持保守：被忽略或过期的提示不得反复回来（AGENTS.md 明文）。
- 提醒相关的 SharedPreferences 键与 JSON 字段：只能加、不能改，新增必须有默认值。
- 不新增提醒类型、不改提醒时间计算（那是组④与既有策略的范畴）。
- 不把"恢复"变成"重排全部闹钟"：现有实现里 `CourseReminders.sync` 会先 cancel 再排，
  合并入口时**不得**让任一类型被取消后没有重新排上。
